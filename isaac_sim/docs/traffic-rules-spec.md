# 교통 규칙 명세 (백엔드 구현용)

관제(E 백엔드)가 구현할 차량 교통 조율 규칙.
시뮬(F)에서 동작을 검증한 로직을 언어 무관하게 정리했다.
**실물·시뮬 구분 없이 동일하게 적용한다.**

> 관제는 **어디로 갈지만** 정한다. 경로 계획과 장애물 회피는 각 차량의 Nav2 가
> 한다. 관제가 경유점을 일일이 지정하면 예기치 못한 장애물에 대응할 수 없다.

---

## 0. 한 장 요약

```
관제가 켜지면 전원 정지 상태로 시작해 한 대씩 순환로에 올린다(§4).
합류가 끝난 차량에 대해서만 아래를 반복한다.

매 0.5초, 차량마다:

  telemetry 로 받은 (x, y)  ──사영──▶  순환로 위 거리 s (0~67 m)

  ① 작업 중인가?                    → 예: 아무것도 안 함
  ② 앞차가 가까운가? (s 기준)        → 예: control HOLD
  ③ 20초 정체인가?                  → 예: 같은 목표 재전송
  ④ 목적지 결정 (모서리 or 스테이션)
  ⑤ 목표가 바뀌었나?                → 예: task 전송

보내는 것은 3종류뿐:
  task  {pickup:{x,y,yaw}}        다음 목적지
  control {"command":"HOLD"}      대기
  control {"command":"RESUME"}    재개
```

## 2. 핵심 계산 — 순환로 위 거리(호장)

### 2.1 왜 좌표 차이로 하면 안 되나

```
F02 (15.5, 20)  오른쪽 통로, 북쪽으로 이동 중
F03 ( 5.0, 20)  왼쪽 통로,  남쪽으로 이동 중

직선거리 = 10.5 m   →  "가깝다" 고 판단해 멈춤   ✗ 잘못
```

실제로는 가운데 랙을 사이에 둔 **반대편 통로**다. 부딪힐 일이 없다.
또 "앞/뒤" 를 x 나 y 로 정의할 수 없다 — 차가 북쪽으로 가는지 서쪽으로 가는지에
따라 앞의 방향이 달라지기 때문이다.

**해결**: 순환로를 0~67 m 짜리 1차원 자로 보고, 모든 위치를 그 위의 한 점 `s`
로 바꾼다.

```
F02 → s = 16.0        (오른쪽 통로, C0 에서 16 m)
F03 → s = 40.5        (왼쪽 통로,  C2 에서 7 m)

gap(F02→F03) = (40.5 − 16.0) mod 67 = 24.5 m   →  멀다, 안 멈춤   ✓ 올바름
```

### 2.2 사영: 위치 → (s, 이탈거리)

```
project(p):
    bestD = ∞ ; bestS = 0 ; acc = 0
    for each segment (a → b) in loop:
        L  = |b − a|
        t  = ((p−a)·(b−a)) / L²        # 내적
        t  = clamp(t, 0, 1)            # 선분 밖으로 나가지 않게
        c  = a + t·(b−a)               # 선분 위 최근접점
        d  = |p − c|
        if d < bestD:
            bestD = d ; bestS = acc + t·L
        acc += L
    return (bestS, bestD)              # (호장, 이탈거리)
```

- **s** — 앞뒤 판단에 쓴다
- **이탈거리** — `OFF_LOOP_TOL`(4 m) 초과면 그 차량은 교통 판단에서 뺀다
  (랙에 도킹해 들어간 차는 통로를 막는 것이 아니다)

### 2.3 진행 방향 남은 거리

```
gap(sFrom, sTo) = ((sTo − sFrom) mod 67.0 + 67.0) mod 67.0
```

| 내 s | 상대 s | gap | 해석 |
|---|---|---|---|
| 61.5 | 1.0 | **6.5** | 앞에 6.5 m (한 바퀴 감김 자동 처리) |
| 1.0 | 61.5 | **60.5** | 사실상 뒤 (60 m 돌아야 만남) |

`mod` 하나로 앞뒤 판정과 wrap-around 가 동시에 해결된다.

### 2.4 다음 모서리

```
nextCorner(s):
    최소 gap(s, cornerS[i]) 를 갖는 i        # 단, gap ≤ 1.5 m 이면 이미 지난 것으로 보고
                                             #     gap + 67 로 취급해 그 다음을 고른다
    return corner[i]
```

## 3. 차량 상태 (관제가 들고 있을 값)

| 필드 | 타입 | 의미 |
|---|---|---|
| `state` | enum | `UNKNOWN` / `IDLE` / `ACTIVE` / `LOST` — 생애주기 (§4) |
| `phase` | enum | `TO_BAY` / `LOAD` / `TO_EXIT` / `TO_RACK` / `RACK` — 작업 단계 |
| `lastSeenAt` | ts | 마지막 telemetry 시각 (2초 넘으면 `LOST`) |
| `target` | string | 지금 향하는 스테이션 이름 |
| `held` | bool | 교통 규칙으로 정지시킨 상태인가 |
| `rackIndex` | int | 다음에 쓸 랙 번호 (차량마다 여러 랙 번갈아) |
| `workUntil` | timestamp | 작업(적재/랙적재) 종료 예정 시각 |
| `lastSent` | Pose | 마지막으로 보낸 목표 (중복 전송 방지) |
| `lastPos`, `lastMoveAt` | Pose, ts | 정체 감시용 |

```
stoppedKind(v):                      # 이 차량이 "멈춰 있는" 상태인가
    if v.phase in (LOAD, RACK):  return "작업중"
    if v.held:                   return "대기중"
    return null
```

전역 상태 둘:

| 필드 | 의미 |
|---|---|
| `bayOwner` | 바이를 쓰고 있는 차량 ID (없으면 null) |
| `releaseCooldown` | 다음 합류 허가까지 남은 시간 (§4.3) |

## 4. 관제 생애주기 (기동 · 합류 · 복구)

규칙을 언제 적용하는지에 대한 장이다. **관제가 켜지는 순간부터 차량이
움직이기까지의 절차**와, 통신이 끊겼다 돌아왔을 때의 처리를 정한다.

### 4.1 차량 상태 5단계

관제는 차량마다 아래 상태를 하나 갖는다.

```
  UNKNOWN ──telemetry 도착──▶ IDLE ──합류 허가──▶ ACTIVE
                                ▲                   │
                                │                   │ telemetry 2초 끊김
                                └───────────────────┘
                                      LOST
```

| 상태 | 뜻 | 관제의 행동 |
|---|---|---|
| `UNKNOWN` | telemetry 를 한 번도 못 받음 | 없는 차량으로 취급. 아무것도 안 함 |
| `IDLE` | 살아있지만 아직 합류 전 | **명령을 보내지 않는다** (= 정지) |
| `ACTIVE` | 합류 완료, 정상 운영 | 규칙 1~5 를 적용해 명령 |
| `LOST` | 2초 이상 telemetry 없음 | 명령 중단. **다른 차량에겐 장애물로만 취급** |
| (복구) | LOST 였다가 telemetry 재개 | `IDLE` 로 되돌려 **합류 절차를 처음부터** |

> **명령을 안 보내는 것이 곧 정지다.** 차량은 명령이 끊기면 스스로 멈추므로
> (시뮬 0.5초 워치독), `IDLE` 상태에 굳이 `HOLD` 를 보낼 필요가 없다.

### 4.2 기동 절차

관제가 처음 켜졌을 때(또는 재시작했을 때).

```
1. 모든 차량을 UNKNOWN 으로 시작한다.
2. telemetry 가 오는 차량을 IDLE 로 올린다.
3. IDLE 인 차량을 한 대씩 ACTIVE 로 올린다 (§4.3 합류 규칙).
4. ACTIVE 가 된 차량부터 규칙 1~5 를 적용한다.
```

**재시작해도 같은 절차를 쓴다.** 관제가 죽었다 살아나면 차량들은 창고
여기저기 흩어져 있는데, 전원 `IDLE` 부터 시작하므로 자연스럽게 정리된다.

### 4.3 합류 규칙 (한 대씩 올리기)

전원이 동시에 출발하면 간격 없이 몰려 바로 서로를 막는다. 그래서 한 대씩.

```
매 0.5초:
    if 마지막 합류 후 3초(ENTRY_INTERVAL)가 안 지났으면:  아무것도 안 함

    IDLE 인 차량을 ID 순으로 하나 고른다
        sMe = project(그 차의 pose).s
        앞에 있는 ACTIVE 차량까지의 gap 을 구한다
            (순환로에서 4m 넘게 벗어난 차량은 세지 않는다)

        if gap < 10m (ENTRY_HEADWAY):
            → 이번 주기엔 아무도 올리지 않는다 (다음 주기에 재시도)
        else:
            → 그 차량을 ACTIVE 로 올리고, 첫 목표를 보낸다
            → 3초 쿨다운 시작. 이번 주기는 여기서 끝
```

**한 주기에 한 대만** 올린다. 두 대를 동시에 올리면 간격 검사가 무의미해진다.

### 4.4 합류 전 점검

`IDLE` → `ACTIVE` 로 올릴 때, 그 차량이 순환로에 제대로 서 있는지 본다.

| 확인 | 판단 | 첫 목표를 무엇으로 |
|---|---|---|
| 순환로 위에 있나 | `project().이탈거리 ≤ 4m` | 정상: 진행 방향 다음 모서리 |
| 벗어나 있나 | `이탈거리 > 4m` | **가장 가까운 순환로 지점** 먼저 |
| 방향이 맞나 | `pose.yaw` vs 그 지점의 진행 방향 | 90° 이상 어긋나면 넓은 구간에서 정렬 후 합류 |

> 후륜조향 차량은 제자리 회전을 못 한다. 역방향으로 서 있으면 크게 돌아야
> 하므로, **시작 위치는 진행 방향을 보도록 배치**하는 것이 좋다.

### 4.5 통신이 끊겼을 때

```
if now − 마지막 telemetry 시각 > 2초:
    상태를 LOST 로 바꾼다
    그 차량에 명령 전송을 중단한다
    다른 차량의 교통 판단에서는 계속 '장애물' 로 센다
        (마지막으로 알던 위치를 그대로 쓴다)
```

**복구되면 `IDLE` 로 되돌린다.** 곧바로 `ACTIVE` 로 올리면 통신이 복구된
차가 갑자기 튀어나와 위험하다. 합류 절차(§4.3)를 처음부터 다시 밟는다.

### 4.6 기동 타임라인 예

차량 두 대가 5m 간격으로 서 있는 상태에서 관제를 켠 경우.

| 시각 | 일어나는 일 |
|---|---|
| 0.0 s | 관제 기동. 두 대 모두 `UNKNOWN` |
| 0.3 s | 양쪽 telemetry 도착 → 둘 다 `IDLE`. **명령 없음 = 정지** |
| 0.5 s | sim02 검사: 앞에 ACTIVE 없음 → **sim02 `ACTIVE`**, 첫 목표 전송 |
| 1.0 s | sim03 검사: 쿨다운 중(3초) → 대기 |
| 3.5 s | sim03 검사: 앞에 sim02 이 5m → 10m 미만이라 **보류** |
| 6.0 s | sim02 이 멀어져 gap 12m → **sim03 `ACTIVE`**, 첫 목표 전송 |
| 이후 | 둘 다 규칙 1~5 로 정상 운영 |

## 5. 판단 조건 — 순서대로

매 `TICK`(0.5 s) 마다 차량 하나씩 아래 순서로 검사한다. **순서가 중요하다.**

### 조건 −1 — 합류했는가

```
if v.state != ACTIVE:   아무 명령도 보내지 않는다  → 이 차량 처리 종료
```

`UNKNOWN`(아직 안 보임) · `IDLE`(합류 전) · `LOST`(통신 끊김) 인 차량에는
명령을 보내지 않는다. 상태 전이와 합류 절차는 **§4 관제 생애주기** 참고.

### 조건 0 — 작업 중인가

```
if phase in (LOAD, RACK):
    if now < workUntil:   아무 명령도 보내지 않는다 (제자리)
    else:                 다음 phase 로 전이 (§7)
    → 이 차량 처리 종료
```

이 차량은 뒤차 입장에서 "작업중" 장애물이 된다.

### 조건 1 — 앞차가 막는가 (규칙 2)

```
blocker(me):
    sMe = project(me.pose).s
    nearest = null
    for other in vehicles, other ≠ me:
        (sO, off) = project(other.pose)
        if off > OFF_LOOP_TOL:  continue          # 조건 A: 순환로 밖 차량 제외
        g = gap(sMe, sO)
        if nearest == null or g < nearest.gap:  nearest = (g, other)

    if nearest == null:  return null
    kind = stoppedKind(nearest.other)             # 조건 B: 작업중 / 조건 C: 대기중
    if kind ≠ null and nearest.gap < HOLD_DIST:  return kind      # 조건 D (9 m)
    if nearest.gap < SAFE_DIST:                  return "근접"    # 조건 E (6 m)
    return null
```

| 조건 | 기준 | 이유 |
|---|---|---|
| **A** | 이탈 > 4 m 제외 | 랙에 도킹한 차는 통로를 막지 않는다 |
| **B** | `phase ∈ (LOAD, RACK)` | 오래 서 있을 예정 |
| **C** | `held` | 연쇄 정지(줄서기) |
| **D** | 멈춘 차 < 9 m | 오래 서 있으므로 여유를 더 준다 |
| **E** | 움직이는 차 < 6 m | 곧 멀어지므로 가까워도 된다 |

차체가 3.8 m 이므로 6 m 면 앞뒤 1.1 m, 9 m 면 2.6 m 여유.

```
if blocker ≠ null:
    if not v.held:  publish control HOLD ; v.held = true
    v.lastMoveAt = now                    # 의도적 정지는 정체로 세지 않는다
    → 처리 종료
else if v.held:
    publish control RESUME ; v.held = false ; v.lastSent = null
```

> `v.lastSent = null` 을 반드시 함께 한다. HOLD 로 목표를 취소했으므로
> 같은 목표라도 다시 보내야 한다.

### 조건 2 — 정체인가 (규칙 4)

```
if dist(pos, lastPos) > STALL_MOVE:            # 0.3 m
    lastPos = pos ; lastMoveAt = now
else if now − lastMoveAt > STALL_SEC:          # 조건 F (20 s)
    resendCount++
    v.lastSent = null                          # 같은 목표를 다시 보내게
    lastMoveAt  = now
    if resendCount % 3 == 0:  목표 스테이션을 다시 계산
```

목표가 조용히 실패해도 스스로 회복하는 장치. 조건 1 로 멈춘 경우는
`lastMoveAt` 을 갱신했으므로 오탐이 없다.

### 조건 3 — 어디로 보낼 것인가

```
st = station[v.target]

# 조건 G — 바이 탈출은 순환로를 타지 않는다
if phase == TO_EXIT:
    if dist(pos, st) < ARRIVE_TOL:  onArrive()
    else:                           send task(st)
    → 종료
```

> **조건 G 가 없으면 66 m 를 한 바퀴 돈다.** EXIT(15.5, 4)는 BAY(17, 5) 바로
> 뒤 1.8 m 인데 s 로는 1.0 → 0.0 이라 일방통행으로는 거의 한 바퀴다.
> 짧은 후진·정렬이므로 예외로 직행시킨다. (시뮬에서 실제로 겪은 버그)

```
# 조건 H — 이미 스테이션에 접근 중
if v.approaching:
    if dist(pos, st) < ARRIVE_TOL:  onArrive()      # 직선거리 1.5 m
    else:                           send task(st)
    → 종료

# 조건 I — 진입점이 가까워졌는가
gapToEntry = gap(sMe, entryS[v.target])
if gapToEntry ≤ APPROACH_TRIGGER:                   # 4 m
    (목표가 BAY 면 조건 4 를 먼저 검사)
    v.approaching = true ; send task(st)
else:
    send task(nextCorner(sMe))                      # 순환 계속
```

도착 판정을 **직선거리**로 하는 이유: 스테이션이 순환로에서 벗어나 있을 수
있다(BAY 1.5 m, B 랙 1.0 m). 호장으로 재면 도착을 인식하지 못한다.

### 조건 4 — 바이를 쓸 수 있는가 (규칙 3)

조건 I 가 만족되고 목표가 **BAY** 일 때만 검사한다.

```
if bayOwner ∉ (null, me):
    send task(nextCorner(sMe))          # 조건 J: 멈추지 않고 계속 순환 (대기 선회)
    → 종료
if bayOwner == null:
    bayOwner = me                       # 조건 K: 예약
→ 바이로 진입
```

> **조건 J 가 핵심이다.** 바이를 못 쓰는 차를 차선에 세우면:
> ```
> B 가 바이 기다리며 정지 → A 가 그 뒤에서 막힘
> → A 는 바이를 비워야 하는데 갈 수 없음 → 교착
> ```
> 시뮬에서 이 교착이 실제로 재현됐다. 그래서 **대기 중에도 계속 돈다**
> (비행기 홀딩 패턴).

**반납**: EXIT 에 도착한 시점에 `bayOwner = null`. 바이에서 완전히 빠져나온
때다.

### 조건 5 — 메시지를 보낼 것인가

```
if next ≠ v.lastSent:                   # 조건 L
    publish task {pickup: next}
    v.lastSent = next
```

> 같은 목표를 0.5 초마다 반복 전송하면 차량 Nav2 가 계속 재계획해 주행이
> 끊긴다. **목표가 바뀔 때만** 보낸다.

## 6. 판단 흐름도

```
state == ACTIVE? (조건 −1)     ─아니오→ 명령 없음 (= 정지)
   │예
작업 중? (조건 0)              ─예→ 대기
   │아니오
앞차가 막나? (A~E)             ─예→ control HOLD
   │아니오 (막혔다 풀렸으면 RESUME)
20초 정체? (F)                 ─예→ lastSent 비움 (재전송 유도)
   │
목표가 EXIT? (G)               ─예→ EXIT 좌표 직행
   │아니오
접근 중? (H)                   ─예→ 도착판정(1.5m) or 스테이션 전송
   │아니오
진입점 4m 이내? (I)            ─아니오→ 다음 모서리 전송
   │예
   └ 목표가 BAY?
        남이 사용 중? (J)      ─예→ 다음 모서리 전송 (대기 선회)
        비어 있음? (K)         ─예→ 예약 후 스테이션 전송
   │
목표가 바뀌었나? (L)           ─예→ 전송 / 아니오→ 안 보냄
```

## 7. 작업 주기 (phase 전이)

```
TO_BAY  ──도착──▶ LOAD          task 없음. 화물 명령 후 workUntil = now + 6 s
LOAD    ──시간──▶ TO_EXIT       목표 = EXIT
TO_EXIT ──도착──▶ TO_RACK       bayOwner = null (반납), 다음 랙 선택
TO_RACK ──도착──▶ RACK          랙 적재 명령 후 workUntil = now + 30 s
RACK    ──시간──▶ TO_BAY        주기 완료, 다시 바이로
```

차량별 랙 배정 예:

| 차량 | 사용할 랙 |
|---|---|
| sim02 (SIM_F02) | A1 → A2 → A1 → … |
| sim03 (SIM_F03) | B1 → B2 → B1 → … |
| fk01 (실물) | 합의 후 배정 |

## 8. 메시지

### 7.1 받는 것 — 차량 telemetry (10 Hz)

```json
fast/v1/vehicle/{id}/telemetry
{
  "vehicleId": "sim02",
  "ts": 1785000000000,
  "pose": { "x": 12.34, "y": 5.67, "yaw": 1.5708 },
  "state": "MOVING",
  "loaded": true,
  "forkHeight": 1.35
}
```

`pose` 만 있으면 규칙 2·3 이 동작한다. `state`·`loaded` 는 작업 판단에 쓴다.

### 7.2 보내는 것

```json
// 다음 목적지
fast/v1/vehicle/{id}/task
{ "taskId": "L-0042", "ts": 1785000000000,
  "pickup": { "x": 15.5, "y": 27.0, "yaw": 1.5708 } }

// 대기 / 재개
fast/v1/vehicle/{id}/control
{ "ts": 1785000000000, "command": "HOLD" }
{ "ts": 1785000000000, "command": "RESUME" }
```

⚠️ **HOLD 중에는 차량이 새 task 를 무시한다.** 반드시 `RESUME` 을 먼저 보내고
다음 목표를 준다.

### 7.3 한 바퀴 도는 메시지 예

```jsonc
// 차량이 (15.5, 5) 부근, s ≈ 1 → 다음 모서리 C1
{"taskId":"L-001","pickup":{"x":15.5,"y":27.0,"yaw":1.5708}}
// telemetry 로 (15.5,27) 도착 확인(1.5 m 이내) → C2
{"taskId":"L-002","pickup":{"x":5.0,"y":27.0,"yaw":3.1416}}
// → C3
{"taskId":"L-003","pickup":{"x":5.0,"y":4.0,"yaw":-1.5708}}
// → C0 (한 바퀴)
{"taskId":"L-004","pickup":{"x":15.5,"y":4.0,"yaw":0.0}}
```

## 9. 안전 — 반드시 지킬 것

1. **MQTT 는 지연이 있다.** 관제의 `HOLD` 는 여유 있는 대기용이다.
   실물의 **비상정지는 차량 자체 센서**로 해야 한다 (interface-spec 7절).
   200 ms KPI 를 MQTT 경로에 적용하면 안 된다.
2. **통신이 끊긴 차량은 제어 불가로 본다.** telemetry 가 2 초 이상 끊기면
   그 차량을 "움직이는 장애물" 로만 취급하고(명령 전송 중단), 다른 차량이
   피하도록 한다.
3. **관제가 죽어도 차량은 안전해야 한다.** 차량은 명령이 끊기면 스스로
   정지한다(시뮬은 0.5 초 워치독).
4. **HOLD 와 ESTOP 을 구분한다.** HOLD = 교통 대기, ESTOP = 비상.

## 11. 대안 — 구역(zone) 방식

호장 계산이 부담되면 맵을 구역으로 나눠 "한 구역에 한 대" 로 단순화할 수 있다.

| | 호장 방식 (본 문서) | 구역 방식 |
|---|---|---|
| 정밀도 | m 단위 간격 조절 | 구역 단위 (있다/없다) |
| 구현 | 사영 수식 필요 | 사각형 포함 판정만 |
| 간격 조절 | `HOLD_DIST` 로 미세 조정 | 불가 (구역 크기가 곧 간격) |
| 적합 | 넓은 통로에서 줄서기 | 좁은 교차로·단선 구간 |

실제 AGV 시스템은 **둘을 섞는다.** 본 명세도 순환로는 호장, **바이는 구역
예약**(조건 4)으로 되어 있다.
