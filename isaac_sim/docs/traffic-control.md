# 차량 간 충돌 방지 설계 (F 파트)

2026-08-03~04 실험 결과를 토대로 한 결론과 구현 방향.

---

## 1. 결론 먼저

**"두 지게차가 라이다로 서로를 보고 실시간으로 비켜 지나간다"는 방식은 버린다.**
대신 **3층 구조**로 간다.

| 층 | 이름 | 하는 일 | 담당 |
|---|---|---|---|
| 1층 | **관제 교통제어** | 애초에 두 대가 같은 공간에 안 들어가게 배차/대기 | 관제(F+E) |
| 2층 | **차량 안전정지** | 그래도 앞에 뭔가 있으면 무조건 정지 | 차량(F, 실물은 C) |
| 3층 | Nav2 지역 회피 | 넓은 곳의 예기치 못한 장애물만 | Nav2 기본값 |

1층이 주력, 2층이 안전망. 3층은 있으면 좋은 정도로 두고 튜닝에 시간 쓰지 않는다.

## 2. 왜 실시간 상호 회피가 안 됐나 (실측 근거)

라이다·TF·costmap·경로 생성은 **전부 정상 작동을 확인했다.**
- 라이다: F03 방향 측정 2.68 m / 기대 2.72 m → 정상
- costmap 마킹 → 경로 휨 확인 (계획 y 1.98~3.98)
- 실제 궤적도 휨 확인 (휨폭 1.62 m) → **회피 동작 자체는 됐다**

그럼에도 "완전히 안 스치고 부드럽게"가 안 된 이유는 아래 4가지이며, 전부 **튜닝으로 못 넘는 구조적 한계**다.

### (1) 라이다는 상대의 앞면만 본다
빛이 상대 차체를 못 뚫으므로, costmap 에는 **F03 의 앞면 한 겹**만 찍힌다.
3.8 m 짜리 몸통이 "선 하나"로 인식된다. 그래서 그 선만 피하면 몸통을 스친다.
→ inflation 으로 부풀려 덮어야 하는데, 그게 (2) 문제를 만든다.

### (2) inflation 딜레마
- 작게(0.55~1.0): 몸통을 못 덮어 **스침**
- 크게(1.5~1.9): 위험원이 통로를 막아 `Starting point in lethal space!` → **출발조차 못 함**

지게차 폭 1.9 m × 2대 = 3.8 m. 여기에 여유까지 하면 통로가 **5 m 이상** 뚫려 있어야
두 대가 스쳐 지나갈 수 있다. 창고 통로는 그만큼 넓지 않다.
→ 애초에 **좁은 통로에서 두 대가 교차하는 것 자체가 물리적으로 무리**다.

### (3) 후륜조향의 한계
제자리 회전이 불가능해서, 경로 재계산이 실패하면 Nav2 의 복구 동작이 전부 헛돈다.
- `REEDS_SHEPP`: 후진 쿠스프 → 앞뒤로 꿈틀 (부딪히려는 것처럼 보임)
- `DUBIN`: 후진 불가 → 방향 맞추려 **한 바퀴 크게 돎**

둘 다 목표 heading 을 맞추려다 생긴다. `yaw_goal_tolerance: 3.14` 로 방향을 안 따지게
하면 상당히 줄어든다(적용 완료).

### (4) kinematic + collision 조합이 시뮬을 죽인다
차량은 물리 반응이 없는 kinematic 이라 겹쳐도 안 튕긴다. 그런데 라이다가 서로를
보게 하려고 collision 은 켜 뒀다. → 두 차가 **깊게 겹치면 PhysX 접촉 계산이 폭발**,
Isaac 이 사실상 정지하고 `/clock` 발행이 멈춘다.

`/clock` 이 멈추면 use_sim_time 을 쓰는 **Nav2 전체와 위치 리셋이 같이 얼어붙는다.**
그 상태에서 목표를 주면 "안 움직이는데 SUCCEEDED" 가 뜬다.
→ 오늘 후반의 이상 증상 상당수가 이것이었다. **"통과"가 clock 을 죽인다.**

## 3. 1층 — 관제 교통제어 (주력)

실제 물류 AGV/AMR 도 상호 회피가 아니라 **중앙 교통관제**로 푼다.
"바이에 차 있으면 다음 차는 대기" 라는 규칙이 정확히 이 방식이다.

### 존(zone) 정의
맵을 배타 구역으로 나눈다. 한 존에는 한 대만.

| 존 | 좌표(sim, 10배) | 용도 |
|---|---|---|
| `BAY_IN` | (16.5, 5) 반경 2.5 | 입고 바이 |
| `WAIT_IN` | (10, 5) | 바이 대기점 |
| `RACK_A` | A1/A2 approach | 랙 A 적재 |
| `RACK_B` | B1/B2 approach | 랙 B 적재 |
| `IDLE` | (3, 5) | 대기/충전 |

### 예약 프로토콜
```
차량이 다음 존에 들어가려면:
  관제에 예약 요청  ->  비어있으면 승인, 아니면 보류
  보류면 차량은 존 경계 앞 대기점에 goal 을 받고 정지
  존을 벗어나면 해제 -> 대기 중이던 차량에 승인
```

관제가 각 차량의 `navigate_to_pose` goal 을 **직접 결정해서** 보낸다.
차량은 스스로 판단하지 않는다. 그래서 결정론적이고 데모에서 실패하지 않는다.

### 구현 상태
`nav2/scripts/coordinator.py` 에 최소 버전이 있다.
- A(F03)가 BAY_IN 반경 2.5 m 안에 있으면 → B(F02)를 WAIT_IN 으로
- A 가 벗어나면 → B 를 BAY_IN 으로

확장할 것: 존 테이블화, 3대 이상, 랙 존까지 적용, MQTT 로 관제 명령/상태 발행.

### MQTT 연동 (E 팀 백엔드와)
이미 `docs/interface-spec.md` 에 잡아둔 형식을 그대로 쓴다.
- 차량 → 관제: 위치/상태 (`forklift/{ID}/location`, `/status`)
- 관제 → 차량: 목적지 지시, 대기/진행 명령

관제 로직을 **백엔드(E)로 옮기면** 그대로 실물에도 적용된다. 시뮬은 같은 토픽을
쓰므로 실물↔시뮬 구분이 안 되는 원래 목표와도 맞는다.

## 4. 2층 — 차량 내장 안전정지 (안전망)

실물 지게차에도 안전 스캐너가 달려 있고, **컨트롤러가 뭐라고 명령하든**
앞에 사람이/물체가 있으면 정지시킨다. 시뮬도 똑같이 만든다.

### 왜 Nav2 가 아니라 차량 안에 넣나
- Nav2 collision_monitor 는 별도 lifecycle 노드라 지금 launch 구조에 끼우기 번거롭다
- 차량 노드(`kinematic_vehicle.py`)는 이미 `/scan` 을 받을 수 있고 cmd_vel 을 직접 소비한다
- **실물 구조(안전 PLC가 최종 차단)와 동일** → 트윈 정합성이 좋다

### 로직
```
매 프레임:
  전방 ±30° 라이다 최소거리 d
  d < STOP_DIST(=3.0 m)   -> cmd_v = 0        (정지)
  d < SLOW_DIST(=5.0 m)   -> cmd_v *= 0.3     (감속)
  그 외                    -> 그대로
```
후진 중(v<0)에는 전방 검사를 하지 않는다.

이것만 넣으면 **두 대가 절대 겹치지 않는다.** 겹침이 사라지면 PhysX 폭발도,
`/clock` 사망도 사라진다. 오늘 겪은 불안정의 큰 축이 같이 해결된다.

데모 그림도 좋다 — "앞차를 감지하고 스스로 멈추는 지게차".

넓은 곳의 예기치 못한 장애물용으로만 남긴다. 현재 값에서 더 만지지 않는다.

## 6. 운영 규칙 (오늘 얻은 것)

지키지 않으면 원인 불명 증상이 재발한다.

1. **Nav2 는 한 번만 띄운다.** 재시작 전 반드시 pkill 로 0 확인.
   좀비가 쌓이면 cmd_vel 발행자가 5개가 되고 **가짜 SUCCEEDED** 가 뜬다.
2. **순간이동 리셋(v.x=…) 대신 goal 로 이동시킨다.** 꼭 리셋하면 3초 후 TF 확인.
   stale TF 상태에서 goal 을 주면 "안 움직이는데 SUCCEEDED".
3. **`/clock` 이 도는지 먼저 확인한다.** (`ros2 topic hz /clock`)
   멈춰 있으면 Nav2 도 리셋도 전부 무의미하다. Isaac Stop→Play.
4. **두 차를 겹치게 두지 않는다.** 겹치면 PhysX 폭발 → clock 사망.
   2층 안전정지가 들어가면 자동으로 지켜진다.
5. **라이다 `minReflectionRangeM=200` 은 건드리지 않는다.** 바꾸면 전 측정이 -1.
   라이다가 죽으면 Stop→Play 로 파이프라인 리셋.
6. FPS 가 20 아래로 떨어지면 ToF 라이다·카메라를 끈다. (RTX 4050 6GB 한계)
