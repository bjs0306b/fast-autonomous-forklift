## 0. 한 줄 요약

랙은 물리적으로 **바닥(0층)과 선반(1층)** 두 층인데, **계약에는 층 개념이 없습니다.**
백엔드는 48칸으로 넓혀 두었고, 시뮬이 층을 받을 수 있게 키 하나만 추가해 주시면 됩니다.

## 2. 층 높이 (F팀 실측, 2026-08-10)

```
0층 칸 높이 = 1.325 (시뮬) = 0.1325 실물   ← 바닥 ~ 1층 선반. 실측 0.14
1층 칸 높이 = 2.0   (시뮬) = 0.2    실물   ← 1층 선반 ~ 2층 선반

1층 선반 윗면 = 1.325 (시뮬)  ← _SHELF_Z · place_z 와 같은 값. 포크 목표
```

| 층 | 구간(시뮬) | 유효 높이 | 포크 목표(시뮬) |
|---|---|---|---|
| **0층**(바닥) | 높이 1.325 | **0.14 실물**(실측) | **0.0** |
| **1층**(선반) | 높이 2.0 | **0.2 실물** | **1.325** |

**2층은 만들지 않습니다** — 있기는 하나 지게차가 물리적으로 닿지 못해 팀이 제외했습니다.

### 어느 층에 놓이는가

```
required = 화물높이 + 팔레트 0.012 + 여유 0.025      (모형 스케일)

0층  0.14 ≥ required  →  화물 ≤ 0.103 m (10.3 cm)
1층  0.2  ≥ required  →  화물 ≤ 0.163 m (16.3 cm)
```

- **10.3 cm 이하** — 두 층 다 들어갑니다. 낮은 층 먼저이므로 **0층**
- **10.3 ~ 16.3 cm** — 0층에 안 들어갑니다. **1층으로 올라갑니다**
- **16.3 cm 초과** — 어느 층에도 안 들어갑니다 (`NO_AVAILABLE_STORAGE_SLOT`)

## 3. 제안 — 이름 규칙

**지금 도는 시연을 깨지 않는 것**이 제1 조건입니다. 그래서 기존 이름을 그대로 둡니다.

```
1층(선반)   A1     ← 변경 없음
0층(바닥)   A1F    ← 신규.  F = Floor
```

`A1F`, `A2F` … `A12F`, `B1F` … `B12F` — 24개가 늘어 총 48개가 됩니다.

### F팀이 할 일

**1) `cargo_demo.py`** — 바닥 키를 추가합니다. 기존 키는 손대지 않습니다.

```python
_FLOOR_Z = 0.0                       # 바닥에 놓는 높이 (실측으로 조정)

for _g, _cfg in _RACKS.items():
    for _i, _y in enumerate(_SLOT_Y, start=1):
        RACK_SLOTS[f"{_g}{_i}"] = {          # 기존 = 선반
            "approach": (_cfg["approach_x"], _y, _YAW_WEST),
            "dock":     (_cfg["dock_x"],     _y, _YAW_WEST),
            "place":    (_cfg["place_x"],    _y, _SHELF_Z),
        }
        RACK_SLOTS[f"{_g}{_i}F"] = {         # 신규 = 바닥
            "approach": (_cfg["approach_x"], _y, _YAW_WEST),
            "dock":     (_cfg["dock_x"],     _y, _YAW_WEST),
            "place":    (_cfg["place_x"],    _y, _FLOOR_Z),
        }
```

접근점·도킹점은 **위아래가 같습니다**(같은 칸의 두 층이므로). 다른 것은 `place` 의 z 뿐입니다.

**2) `rack_slots.json` / `.csv`** — `shelfHeight` 옆에 `floorHeight` 를 더하고,
슬롯 24개를 48개로 늘립니다. 백엔드는 이 파일을 직접 읽지 않지만 **양쪽이 갈라지지
않았는지 대조하는 근거**라 함께 맞춰 주시면 좋겠습니다.

## 4. 백엔드는 이미 준비돼 있습니다

| 항목 | 상태 |
|---|---|
| `storage_slot` 48칸 | `seed-rack-slots-level0.sql` 로 준비. 0층 `AF01..AF12` · `BF01..BF12` 신규 |
| 층별 높이 | 0층 `usable_height 0.14` / `fork_height 0.0`, 1층 `0.2` / `1.325` |
| 낮은 층 먼저 | `PlacementService` 가 `fork_height` 오름차순으로 고름 |
| 와이어 변환 | `AF01 → A1F`, `A001 → A1` (`CycleControlService.toWireRackCode`) |
| 주기 배정 | 0층 12칸을 다 채운 뒤 1층 12칸으로 (`traffic.cycle.racks`) |

백엔드 DB 의 `slot_code` 는 `AF01` 형식이고 **와이어로 나갈 때만** `A1F` 로 바뀝니다.
DB 이름을 바꾸지 않는 이유는 `slot_code` 가 PK 이고 `transport_task
.destination_slot_code` 가 FK 로 참조하기 때문입니다 — 이름을 바꾸면 진행 중인 운반
작업이 끊깁니다.

## 5. ⚠️ 맞지 않으면 조용히 실패합니다

**오늘 실제로 겪은 일입니다.** 백엔드가 `A001` 을 보내고 있었는데 시뮬은 `A1` 을
기다리고 있었습니다.

```python
# cargo_demo.py:874
if rack not in RACK_SLOTS:
    print(f"랙 '{rack}' 없음. 사용 가능: {list(RACK_SLOTS)}")
    return False          # ← 예외도 응답도 없다
```

결과는 이랬습니다.

- 차량이 랙 접근점까지 잘 갔다
- `place_rack` 지시도 나갔다
- **그런데 아무것도 놓지 않았다**
- 백엔드는 실패한 줄 모르고 `loaded` 가 안 바뀌니 90초 뒤 타임아웃 → 주기 재시작
- 그것이 무한 반복됐다 (랙에 한 번도 못 가면서 "완료 8주기" 가 찍혔다)

같은 일이 `A1F` 에서 반복되지 않으려면 **양쪽 이름이 정확히 같아야** 합니다.
가능하면 실패를 알 수 있게 해 주시면 더 좋겠습니다 — 예를 들어 알 수 없는 랙 이름이
오면 `fast/v1/vehicle/{id}/event` 로 한 줄 올려 주시면 백엔드가 로그에 남길 수 있습니다.

## 6. F팀에 요청하는 것 — 두 가지

### 6.1 랙 칸 실측 치수

지금 백엔드가 쓰는 값 중 **실측은 하나뿐**이고 나머지는 추정입니다.

| 랙 | 층 | 지금 값(실물 m) | 근거 |
|---|---|---|---|
| A | 0층 | 0.14 | ✅ 실측 |
| A | 1층 | 0.2 | △ "1층 칸 2.0 시뮬" 에서 환산 |
| B | 0층 | 0.14 (A 와 같게 둠) | ❌ 미확보 |
| B | 1층 | 0.2 (A 와 같게 둠) | ❌ 미확보 |

**A·B 랙의 0층·1층 유효 높이를 각각 재 주세요.** 바닥(또는 선반 윗면)에서 위 선반
아랫면까지의 빈 높이입니다. 값을 주시면 `UPDATE` 한 줄로 반영합니다 — 코드는 안 바뀝니다.

함께 확인이 필요한 것:

| 항목 | 지금 가정 | 확인 |
|---|---|---|
| 0층 `place` z | `0.0` | 바닥에 직접 놓는 것이 맞습니까? |
| 0층 0.14 의 정의 | 바닥 ~ 선반 **아랫면** | 선반 **윗면** 높이였다면 `fork_height` 도 `1.325 → 1.40` 이어야 합니다 |
| 선반 두께 | 모름 | 위 항목이 "윗면" 이면 필요합니다 |

두 번째는 `orin-rack-spec.md` §10 이 이미 "확인이 필요한 값" 으로 분류해 둔 것입니다
("1층 선반 높이 0.1325 m — 실측 140 mm 라면 0.140 으로 조정"). 그렇다면 실물 지게차가
7.5 mm 낮게 포크를 올립니다. 시뮬은 자기완결적이라 티가 나지 않습니다.

### 6.2 🔴 박스 높이를 지시대로 만들어 주세요

**시뮬이 `cargo` 의 `height` 를 무시하고 고정 크기 박스를 씁니다.** 2026-08-10 실측입니다.

```
백엔드가 보낸 height 0.15  →  telemetry cargo.h = 0.751
백엔드가 보낸 height 0.30  →  telemetry cargo.h = 0.751   ← 그대로
```

`cargo_demo.py:1094` 가 `h = p.get("height")` 로 값을 읽기는 하는데, 그 값으로 박스
크기를 정하지는 않는 것으로 보입니다.

**이게 되면 좋은 이유**

- 원래 설계가 "카메라가 잰 화물 크기에 따라 적재 위치를 정한다" 입니다. 박스가 늘 같은
  크기면 층이 갈리는 장면을 만들 수 없습니다
- 지금은 그걸 보여주려고 **DB 의 칸 높이를 임시로 낮춰야** 했습니다. 데이터를 건드리는
  방식이라 시연에 쓸 수 없습니다
- 박스 높이가 지시대로 나오면 백엔드가 값만 바꿔 0층·1층을 오가게 할 수 있습니다

가능하면 **박스 높이를 두세 가지로 섞어 스폰**해 주시면 더 좋습니다. 그러면 아무 조작
없이도 층이 갈리는 것이 자연스럽게 보입니다.

현재 임계(실측이 확정되면 함께 바뀝니다):

```
≤ 10.3 cm      0층
10.3 ~ 16.3 cm 1층
> 16.3 cm      적재 불가
```

### 6.3 telemetry `cargo.h` 의 단위

백엔드는 이 값에 `0.1` 을 곱해 실물 m 로 봅니다(`cargo-height-scale`).
`0.751 → 7.51 cm` 로 읽고 있는데, **실제 박스가 7.5 cm 가 맞습니까?**
다르면 그 배수만 고치면 됩니다.
