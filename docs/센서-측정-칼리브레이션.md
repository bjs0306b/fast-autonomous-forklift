# 센서 측정·칼리브레이션 기준

무인 지게차의 IMU·ToF·LiDAR를 **어디에 달고, 무엇을 재고, 어디에 넣고, 무엇으로
합격을 판정하는지** 정리한 기준 문서다.

## 이 문서가 소유하는 것과 아닌 것

**값의 authority는 설정 파일이다.** 문서가 숫자를 옮겨 적으면 두 번째 진실
원천이 생겨 곧 어긋난다.

| 무엇 | 어디 |
|---|---|
| 펌웨어 상수·안전 봉투 | `firmware/esp32/motor_controller/main/config.h` |
| 브리지 파라미터 | `ros2_ws/src/forklift_teleop/config/sensors.yaml` |
| 텔레옵 운전값 | `ros2_ws/src/forklift_teleop/config/teleop.yaml` |
| static TF | `ros2_ws/src/forklift_teleop/launch/sensor_usb.launch.py` |
| LiDAR TF·rf2o | `ros2_ws/src/forklift_teleop/launch/lidar_odometry.launch.py` |
| costmap | `ros2_ws/nav2_params.yaml` |
| EKF | `ros2_ws/src/forklift_teleop/config/ekf.yaml` |

**문서가 소유하는 것**은 무엇을 왜 어떻게 재는지, 합격 기준, 재측정 시점이다.

### 안전 봉투 vs 운전값

`config.h`가 확립한 구분이며 칼리브레이션 작업의 핵심이다.

- **봉투** (`TELEOP_STEERING_MIN/MAX_CDEG`, `TELEOP_MAX_DRIVE_PERCENT`) — 펌웨어에
  박혀 있고 "여기까지 허용"을 뜻한다. 바꾸려면 재플래시
- **운전값** (`teleop.yaml`의 `steering_min/max_cdeg`, `max_drive_percent`) — 실제로
  쓰는 범위. 재플래시 없이 튜닝한다

**튜닝은 항상 운전값 쪽에서 한다.** 봉투를 넓히는 것은 "여기까지 써도 된다"가
아니라 "여기를 넘으면 기구가 상한다"의 완화일 뿐이다.

## 1. 좌표계 규약

**`base_link` = 전륜 구동축 중심.** REP-103을 따른다.

```
+X  포크 방향(전방)      +Y  좌측      +Z  위
회전은 반시계가 양수 — 위에서 봤을 때 좌회전이 +
```

모든 센서 TF, footprint, costmap 프레임이 이 규약을 공유한다. 한 곳이라도 어긋나면
증상이 "가끔 이상함"으로만 나타나 추적이 어렵다.

### z 원점은 축 중심이며 바닥보다 30 mm 위다

**이 한 줄을 모르면 세 센서의 z가 전부 30 mm씩 어긋난다.** 문서에 적혀 있지 않던
것을 2026-08-05 실측으로 확정했다.

ToF를 두 번 쟀다 — 구동축 기준 40 mm, 바닥 기준 70 mm. 그 차이 30 mm가 바닥에서
축 중심까지의 높이다.

```
바닥 ──30mm──> base_link(축 중심) ──40mm──> ToF 광학창   (= 바닥에서 70mm)
```

**교차 확인**: LiDAR `z=0.202`이므로 바닥에서 재면 **0.232 m**여야 한다. 크게
다르면 LiDAR 값이 다른 기준으로 측정된 것이므로 그쪽을 먼저 바로잡는다.

센서를 새로 달 때는 **바닥 기준으로 먼저 재고 30 mm를 빼서** TF에 넣는다. 바닥
기준 값은 `tof_mount_height_m`에도 그대로 쓰이므로 버리지 않는다.

### 실측 static TF (2026-08-05)

값은 [sensor_usb.launch.py](../ros2_ws/src/forklift_teleop/launch/sensor_usb.launch.py)에
있다. 재는 법은 4장 참고.

| 센서 | 측정 원본 | 비고 |
|---|---|---|
| IMU | 구동축에서 뒤로 55 mm, 위로 115 mm | y는 미측정 — 중앙 가정 |
| ToF 좌·우 | 중심에서 각 50 mm, 구동축에서 앞으로 85 mm | 축 기준 높이 40 mm |
| ToF 높이 | 바닥에서 70 mm | 지면 필터용 |

**IMU의 y는 아직 측정되지 않았다.** 중앙(0)으로 두었으므로 좌우로 치우쳐 달았다면
고쳐야 한다. 회전 중심에서 벗어난 IMU는 yaw rate에는 영향이 없지만 TF가 틀리면
가속도 해석과 향후 확장에서 문제가 된다.

### 실측 차체 치수

값은 [ros2_ws/README.md](../ros2_ws/README.md)의 "실측 좌표계" 절에 있다. 요지만:

| 항목 | 기준 |
|---|---|
| 포크 앞끝 | `base_link` 기준 +X |
| 차량 뒤끝 | `base_link` 기준 −X |
| 차체 폭 | 좌우 대칭 ± |
| 축거 | Ackermann 곡률 변환에 사용 |
| footprint | `nav2_params.yaml`의 local·global 양쪽에 동일하게 |

## 2. 센서별 장착 기준

### 2.1 IMU (MPU9250, SPI)

| 항목 | 기준 |
|---|---|
| 위치 | 회전 중심에 가깝게 |
| 고정 | **볼트 또는 강한 접착.** 양면테이프 금지 — 진동이 그대로 노이즈 |
| 거리 | 스텝퍼 드라이버·DC-DC 컨버터에서 최대한 멀리 |
| 배선 | SPI 케이블을 스텝퍼 케이블과 나란히 묶지 않는다 |
| 방향 | Z축이 위(+) |

자기계(AK8963)는 **연결하지 않는다.** 모터 코일·스텝퍼·리니어 스크류가 자기장을
교란하고, 절대 방위는 AMCL이 지도와 대조해 훨씬 정확하게 잡는다.

### 2.2 전면 ToF ×2 (VL53L8CX, I2C1)

| 항목 | 기준 | 근거 |
|---|---|---|
| 높이 | 0.06~0.08 m | 화물 아래(travel 10~15cm)이면서 LiDAR(0.202m)와 0.10m 이상 간격 |
| 피치·롤 | **0° (완전 수평)** | 아래로 기울이면 바닥이 장애물로 찍힌다 |
| 요(벌림) | **0°** | 아래 계산 참고 |
| 좌우 | 포크 티네보다 **바깥** | 안쪽이면 위쪽 행이 자기 포크를 본다 |
| x | 포크 앞끝보다 충분히 뒤 | 아래 제약 |

**벌리지 않는 이유.** 45° 화각을 좌우로 벌리면 먼 곳은 넓어지지만 **정면 근거리에
사각이 생긴다.** 두 센서의 안쪽 경계선이 중심선에서 만나는 지점까지 정면이 빈다.

정면이 확보되기 시작하는 거리 = `y_s / tan(22.5° − 벌림각)`

| 벌림 | 정면 확보 시작 (y_s=0.05) | 1.0m 폭 |
|---|---|---|
| **0°** | **0.121 m** | ±0.464 |
| 10° | 0.226 m | ±0.687 |
| 15° | 0.380 m | ±0.817 |
| 20° | 1.145 m | ±0.966 |

차체 반폭 대비 0°에서도 0.3m 앞 커버가 2배 이상 남는다. 벌려서 얻는 폭은 쓸 데가
없고, 잃는 것은 파렛트 접근 시 정면 근거리다. 명세서 2.3절의 "포크 갭 정면 장착"이
이 뜻이다.

**x 제약**: `x_센서 + 0.121 ≤ x_포크앞끝`. 포크가 닿을 것을 미리 봐야 한다.
차체 앞면이 이보다 앞이면 `y_s`를 더 줄인다.

#### 현재 장착의 포크 앞끝 사각 — 허용 범위

실측 `x=0.085`, `y=±0.050`에서 정면이 확보되기 시작하는 지점은
`0.085 + 0.121 = 0.206`인데 포크 앞끝은 `0.190`이다. 즉 포크 앞끝에 **깊이 16 mm ·
폭 ±6.5 mm의 쐐기꼴 사각**이 남는다.

**그대로 둔다.** 접근하는 물체는 0.206 m 밖에서 이미 보이고, ToF는
`clearing: False`라 costmap에 찍힌 표시가 그 16 mm 구간에서 지워지지 않는다.
파렛트처럼 넓은 대상은 애초에 중심 밖 존이 본다. 없애려면 `x`를 0.069 이하로
당기거나 `y_s`를 줄여야 하는데, 기구 여유가 그만큼 없다.

**다만 폭 13 mm 미만의 가느다란 물체가 정확히 정면에 있을 때만** 마지막 16 mm에서
놓친다는 것은 알고 있어야 한다.

**두 센서를 같은 방향으로 단다.** 한쪽만 90° 돌려 달면 `tof_transpose_zones`가
센서별로 갈려야 하는데 지금 구조는 공용이다.

**배선** — `SPI_I2C_n`을 **반드시 GND로**. 자세한 것은
[펌웨어 README](../firmware/esp32/motor_controller/README.md).

### 2.3 LiDAR (YDLIDAR X4-Pro)

차체 최고점에 **완전 수평·리지드 고정.** 기울기는 거리에 비례해 증폭되어 SLAM
오차가 된다. 그 높이에서 360°가 자기 구조물에 가리지 않아야 한다.

**높이를 바꾸면 세 가지를 확인한다.**

1. `lidar_odometry.launch.py`의 `LIDAR_TRANSLATION` z를 실측으로 갱신 — 필수이고,
   틀려도 에러 없이 조용히 어긋난다
2. VoxelLayer 천장 = `origin_z + z_resolution × z_voxels`. 이보다 높아지면 반환이
   격자 밖이라 marking·clearing이 아예 안 먹는다
3. **ToF보다 높기만 해서는 부족하다.** `z_resolution` 기준 최소 2~3복셀 간격이
   필요하다. 같은 복셀 층을 건드리면 clearing 충돌이 되살아난다

## 3. 칼리브레이션 파라미터

| 파라미터 | 위치 | 재는 법 | 합격 |
|---|---|---|---|
| `gyro_z_sign` | sensors.yaml | 위에서 봤을 때 반시계로 돌린다 | 반시계 = 양수 |
| `IMU_GYRO_SENSITIVITY_LSB_DPS` | config.h | `tools/gyro_scale_check.py` | 360° ±5% |
| `yaw_rate_stddev` | sensors.yaml | **모터 켠 상태** 정지 노이즈 | 실측값. **0 금지** |
| `tof_fov_deg` | sensors.yaml | `tools/tof_geometry_check.py` | 알려진 방위와 일치 |
| `tof_azimuth_sign` | sensors.yaml | 같은 도구, 물체를 옆으로 | 좌측 → +Y |
| `tof_elevation_sign` | sensors.yaml | 같은 도구, 물체를 위로 | 위 → +Z |
| `tof_transpose_zones` | sensors.yaml | 옆으로 옮긴 물체가 고도로 나오면 true | — |
| `tof_mount_height_m` | sensors.yaml | 바닥에서 광학창 중심까지 | 실측 |
| `tof_masked_zones_*` | sensors.yaml | `tools/tof_mask_learn.py` | 빈 공간에서 검출 0 |
| ToF 거리 | — | 평벽 0.5/1.0/2.0 m | ±5% |
| static TF ×3 | sensor_usb.launch.py | 자·캘리퍼스 | 실측 |

### 왜 이 값들이 위험한가

**`yaw_rate_stddev`를 0으로 두면 안 된다.** EKF가 "오차 없는 완벽한 센서"로 착각해
라이다 오도메트리를 완전히 무시한다. IMU를 달고도 나빠지는 전형적인 경로다.

**부호와 전치는 static TF로 못 고친다.** 거울상은 회전이 아니라 반사다. 장착 후에
발견하면 원인이 TF인지 부호인지 구분이 안 돼 훨씬 오래 걸리므로, **벤치에서 먼저**
확정한다. RViz의 Fixed Frame을 `tof_left_link`로 두면 `base_link` TF 없이 검증할 수
있다.

**자이로 스케일은 감도 상수로 고치기 전에 구간 편차를 본다.** 감도는 곱셈 상수라
네 구간을 같은 비율로 바꾼다. 구간이 점점 줄어들면 스케일이 아니라 바이어스
추적기가 회전을 흡수하는 것이고, 그건 `task_imu.c`의 정지 판정 게이트 문제다.

## 3.5 2026-08-06 실측 결과

전 절차를 한 번 통과시킨 기록이다. 값 자체는 설정 파일이 소유하고, 여기에는
**무엇이 합격이었고 무엇이 놀라웠는지**만 남긴다.

| 단계 | 결과 |
|---|---|
| A 링크 | @IMU 100.1 Hz 결번 0 · @TOF 14.9/15.1 Hz · I2C 에러 0 |
| B 자이로 | 4구간 87.1/90.5/88.2/92.3° · 크기 −0.5% · 시계방향=음수 (정상) |
| C 잡음 | **0.010934 rad/s** — 라이다 켠 상태 |
| D 기하 | azimuth −1 · elevation −1 · transpose false · 피치 좌 +3.0° 우 −1.1° |
| E 거리 | 0.5/1.0/2.0 m 에서 좌 −2.8/+1.2/−4.6% · 우 −0.5/+1.5/−3.8% |
| F 마스킹 | **불필요** — 자기 가림 존 0개 |
| I EMI | 스텝퍼 150초 증가 0 · 정지 중 우 ToF 2분에 1건 |
| J 통합 | ToF 가 라이다 사각의 낮은 상자를 마킹, 회전해도 유지 |

### 놀라웠던 것 넷

**1. 라이다가 90° 돌아 달려 있었다.** `LIDAR_ROTATION` 이 0 이라 뒤쪽 벽이 왼쪽에
그려졌다. 화면 문제가 아니다 — rf2o 는 라이다 프레임에서 변위를 재므로, 전진할 때
옆으로 미끄러진다고 계산하고 EKF 가 그 위에 쌓는 자세가 전부 틀어진다. RViz 에서
Fixed Frame 을 base_link 로 두고 **알려진 방향의 벽**을 보면 즉시 드러난다.

**2. C 단계는 라이다를 켜고 재야 한다.** 꺼놓고 재면 0.000722 rad/s 가 나오는데
이는 MPU9250 의 잡음 바닥이고, 켜면 **15배**인 0.010934 가 된다. 라이다는 차체
최고점에서 도는 모터다. 나온 값이 데이터시트 잡음 바닥과 같은 자릿수면 운용 조건이
아니라는 신호다.

**3. 두 ToF 의 피치가 4° 다르다.** 좌 +3.0°, 우 −1.1°. 브래킷이 조절식이 아니라
실측해서 실었다. 피치를 모르는 지면 필터는 축 근처 행의 바닥을 걸러내지 못해
**1 m 앞 가짜 장애물**을 만든다.

**4. 직물 바닥이 단발 반사를 뿌린다.** 자리가 고정되지 않아 마스킹으로는 못 잡고,
`clearing: False` 라 costmap 에 한 번 찍히면 ToF 가 지우지 못한다. 존이 한 번 더
나타나야 믿는 지속성 필터로 잡았다 (`tof_persistence_*`).

### 도구가 못 하는 판정

`tof_wall_check.py` 의 화각 진단에는 물리적 하한이 있다. cos(19.69°)=0.9415 이므로
최외곽 x 는 −5.85% 아래로 못 내려간다. 실측은 −6~9% 였고, 이는 **비스듬한 존에서
거리를 짧게 보고하는 센서 특성**이지 설정으로 고칠 수 있는 것이 아니다. 장애물이
실제보다 가깝게 찍히므로 회피에는 안전한 방향이다.

### 걸려 넘어진 함정

| 증상 | 원인 |
|---|---|
| yaml 을 고쳐도 안 바뀜 | launch 는 `install/` 사본을 읽는다. `colcon build` 필요 |
| 좀비 브리지가 포트 다툼 | `ros2 launch` 는 자식을 남긴다. `pkill -f .../sensor_bridge` |
| numpy 없다는 오류 | ESP-IDF venv 가 ROS 를 가린다. `deactivate` 또는 터미널 분리 |
| `idf.py` 가 파이썬 불일치로 거부 | `./flash.sh` 를 쓴다. `fullclean` 은 하지 말 것 |
| 스캔 구독자가 한 건도 못 받음 | `/scan` 은 Best Effort. `qos_profile_sensor_data` |
| 2 m 벽이 −77% 로 측정됨 | 피치 3° 면 광축이 1.34 m 에서 바닥에 닿는다. 중앙 존은 벽을 못 본다 |

## 4. 측정 절차

**순서대로. 각 단계를 통과한 뒤 다음으로 간다.** 뒤부터 붙이고 디버깅하면 원인을
못 찾는다.

도구는 전부 `firmware/esp32/motor_controller/tools/`에 있다. 포트를 여는 순간
**ESP32가 리셋되고 포크 호밍이 한 번 도니** 주변을 비우고 실행한다.

### A. 링크 건전성

```bash
python3 tools/tof_probe.py
```

| 확인 | 합격 |
|---|---|
| `@IMU` 레이트 | 100 Hz 근처, 결번 0 |
| `@TOF` 레이트 | 센서당 15 Hz 근처, 결번 0 |
| `@TFS` I2C 에러 | **정지 상태에서 0** |
| PCA9685 스캔 | 0.2초 내 완료, 타임아웃 0 |

### B. 자이로 부호·스케일

```bash
ros2 topic echo /imu/data --field angular_velocity.z   # 반시계 = 양수
python3 tools/gyro_scale_check.py                      # 90° × 4
```

십자선을 그은 종이에 보드 한 변을 맞추고 다음 선까지 돌리면 정확히 90°다.
**속도는 상관없다** — 적분은 속도 프로파일과 무관하고, 90°를 1초보다 빠르게만
돌리지 않으면 ±250 dps 포화도 피한다.

### C. 자이로 노이즈 → `yaw_rate_stddev`

```bash
python3 tools/yaw_noise_check.py --seconds 60
```

차량은 정지시키되 **운용할 때 켜져 있는 것은 전부 켠 채로** 잰다. 무엇을 켜고
쟀는지가 값 자체보다 중요하다.

2026-08-06 실측이 그 이유를 그대로 보여준다.

| 조건 | 표준편차 | |
|---|---|---|
| 라이다 꺼짐 | 0.000722 rad/s | 0.041 °/s — 센서 잡음뿐 |
| **라이다 켜짐** | **0.010934 rad/s** | **0.626 °/s** |

**15배 차이다.** 라이다는 차체 최고점에서 도는 모터라 진동이 IMU까지 그대로
온다. 꺼놓고 잰 값을 넣으면 EKF는 IMU를 실제보다 15배 정확한 센서로 믿는다.

판별법: 나온 값이 센서 데이터시트의 잡음 바닥과 같은 자릿수면 기계 진동이 전혀
안 잡힌 것이다. MPU9250은 잡음 밀도에 DLPF 41 Hz를 곱해 약 0.064 °/s이므로,
0.04 °/s가 나왔다면 그건 운용 조건이 아니다.

구동 모터까지 도는 주행 중에는 더 커질 수 있다. 헤딩이 떨리면 주행 상태로 다시
잰다.

**작은 값이 여기서는 위험하지 않은 이유.** `ekf.yaml`에서 yaw rate를 내는 것은
IMU 하나뿐이고 rf2o는 vx/vy만 준다. 둘이 다투지 않으므로 이 값은 얼마나 매끄럽게
따라가느냐만 정한다. 그래도 **0은 안 된다** — 오차 없는 센서라는 뜻이 되어
필터가 다른 입력을 전부 무시한다.

### D. ToF 기하 — 좌우·고도·방위·전치

**여기서 틀리면 나중에 못 고친다.** 거울상은 회전이 아니라 반사라 static TF로
보정되지 않는다. 장착 후에 발견하면 원인이 TF인지 부호인지 구분이 안 돼 훨씬 오래
걸린다.

확정할 것은 네 가지다.

| 항목 | 어디 | 틀리면 |
|---|---|---|
| 좌우 센서 배정 | `config.h`의 LPn/INT GPIO | 토픽·프레임·TF·마스크가 통째로 반전 |
| `tof_elevation_sign` | sensors.yaml | 바닥이 장애물로 찍히거나 천장이 바닥이 됨 |
| `tof_azimuth_sign` | sensors.yaml | 좌우 반전 |
| `tof_transpose_zones` | sensors.yaml | 가로세로 뒤바뀜 |

#### 시작 전 — 이 넷을 먼저 확인한다

측정 실패의 대부분이 여기서 나왔다. 넷 다 증상이 "값이 이상하다"로만 나타난다.

1. **ESP-IDF 환경을 끈다.** `activate_idf_*.sh`가 만든 venv에는 numpy가 없고 ROS의
   것을 가린다. `deactivate` 하거나 터미널을 분리한다. 펌웨어용과 ROS용 터미널을
   따로 두는 편이 낫다
2. **좀비 브리지를 죽인다.** `ros2 run`은 자식을 남기므로 부모만 죽이면 포트를 계속
   물고 있다. 여러 개가 다투면 프레임이 조용히 유실된다

   ```bash
   pkill -f "forklift_teleop/lib/forklift_teleop/sensor_bridge"
   fuser /dev/ttyACM0        # 아무것도 안 나와야 한다
   ```
3. **sensors.yaml을 고쳤으면 `colcon build` 한다.** launch가 읽는 것은
   `install/`의 **사본**이다. `src/`만 고치면 아무 일도 일어나지 않으며, 격자가
   바뀌지 않는 것으로만 드러난다
4. **펌웨어를 고쳤으면 플래시하고 부팅 로그를 본다.**

   ```
   TOF: mapping: left LPn=GPIO14 INT=GPIO2, right LPn=GPIO13 INT=GPIO1
   ```

   이 줄이 없으면 플래시가 안 된 것이다. 프레임에는 센서 위치 정보가 없어서, 이
   줄 없이는 "플래시가 안 됨"과 "매핑이 틀림"을 구분할 수 없다

#### D-0. 좌우 배정

```bash
python3 tools/tof_identify.py
```

**물리적 왼쪽 모듈을 손으로 가린다.** `left` 줄이 죽으면 맞다. 가린 쪽은 유효 존
0/64에 상태 4가 64개로 나온다 — 아무것도 측거하지 못하는 모습이다.

`right`가 죽으면 배선이 교차된 것이다. `config.h`의 LPn·INT GPIO를 **쌍으로**
맞바꾸고 다시 플래시한다. 배선을 다시 만들 필요는 없다.

LPn만 교차돼 있었다면 이제 INT가 어긋나 `is being polled, INT never fired` 경고가
뜬다. 그러면 INT 두 줄만 되돌린다.

#### D-1. 고도 부호 — 바닥으로 판정한다

**받침대를 쓰지 않는다.** 물체를 띄우면 받침이 시야에 함께 들어오고, 도구는 최근접
반사를 집으므로 받침을 잰다. 바닥은 크기·위치·재질이 이미 정해진 목표물이라 받침이
필요 없고 흔들리지도 않는다.

70mm 장착에서 아래쪽 행들이 계산된 거리에서 바닥을 친다.

| 행 | 고도각 | 바닥 거리 |
|---|---|---|
| 7 | −19.7° | 0.208 m |
| 6 | −14.1° | 0.288 m |
| 5 | −8.4° | 0.477 m |

**지면 필터를 먼저 끈다.** 켜져 있으면 바닥 점이 이미 걸러져 아무것도 안 보인다.
`false`를 `flase`로 적으면 YAML에서 불리언이 아니라 문자열이 되어 조용히 참으로
먹는다.

```yaml
tof_ground_filter: false    # 판정 중에만
```

```bash
colcon build --packages-select forklift_teleop      # 잊으면 안 된다
python3 tools/tof_geometry_check.py --topic /tof/left/points --check-floor
```

바닥이 센서보다 **아래(z 음수)**로 나와야 한다. 위로 나오면 물리적으로 불가능하므로
`tof_elevation_sign`을 뒤집는다.

**더 강한 판정**: 격자의 아래쪽 세 행이 전부 비어 있으면 부호가 뒤집힌 것이다.
바닥에서 7cm 위에 있는 수평 센서의 아래쪽 절반이 아무것도 못 볼 수는 없다.

끝나면 `tof_ground_filter: true`로 되돌리고 다시 빌드한다. D-2에서는 바닥이 걸러져
있어야 목표물이 최근접이 된다.

#### D-2. 방위 부호와 전치 — 옆 물체로 판정한다

**배경이 비어 있어야 한다.** 센서 앞 2m 안에 벽·상자·배선이 없는 곳으로 옮긴다.
복도가 좋다. 어수선한 벤치에서는 판정이 불가능하다.

바닥에 높이 140mm쯤 되는 밝은 상자를 세운다(광축이 70mm이므로 중심이 얼추 맞는다).
1m 앞, 옆으로 200~250mm 에 둔다.

**각도는 차량 중심이 아니라 그 센서에서 잰다.** 좌우 ToF 는 중심에서 각 50mm
벌어져 있어, 중심 기준 각을 그대로 넣으면 존 하나만큼 어긋난다. 2026-08-06 실측이
그랬다 — 중심 기준 12.7° 인 상자가 센서 기준으로는 9.93° 였고, 측정된 존 중심
8.44° 와 맞았다.

```
방위각 = atan2(옆거리 - 그 센서의 y오프셋, 앞거리)
```

상자 폭도 각도를 넓히므로 양 끝을 각각 환산해 한 존 안에 들어가는지 본다. 위
실측에서 상자 양 끝은 센서 기준 8.53° 와 11.31° 로, 5.62~11.25° 존에 거의
들어맞았다.

| 조건 | 근거 |
|---|---|
| 폭 50~80mm | 한 존이 1m에서 98mm를 덮는다. 넓으면 여러 존에 걸쳐 모호해진다 |
| 20mm 이상 | 가늘면 반사가 약해 유효로 안 잡힌다 |
| 밝은 색·평면 | 검은 무광은 흡수한다. 면이 센서를 정면으로 보게 둔다 |
| 더 가까운 것 없음 | 도구는 최근접 반사를 집는다 |

```bash
python3 tools/tof_geometry_check.py --topic /tof/left/points --true-azimuth 14.06
```

차체 자체 가림이 목표물보다 가까우면 `--min-range 0.5`로 비켜간다. 그 가림은
절차 F에서 마스킹한다.

**판정은 자동 결론이 아니라 격자로 한다.** 최근접점 자동 판정은 목표물이 아닌 것을
집었을 때 확신에 찬 오답을 낸다.

상자를 **좌 → 우로 옮기며 두 번** 찍고 격자를 비교한다.

| 격자에서 덩어리가 | 판정 |
|---|---|
| 가로로 움직임, 왼쪽에 뒀을 때 왼쪽 열 | 정상 |
| 가로로 움직임, 왼쪽에 뒀을 때 오른쪽 열 | `tof_azimuth_sign: -1` |
| **세로로 움직임** | **전치** — `tof_transpose_zones: true` |

옆으로 옮기는 시험 하나가 방위 부호와 전치를 동시에 가른다. 별도의 고도 시험이
필요 없다.

#### 격자 읽는 법

거리가 **행에만 의존하고 열이 바뀌어도 일정하면** 그건 수평면(바닥 또는 머리 위
구조물)이다. `r = h / sin(고도)`라 방위와 무관하기 때문이다. 단, 그 행의 일부 열만
차 있다면 바닥이 아니다 — 바닥은 더 먼 물체에 가려질 수 없다.

세로 평면은 반대로 **열을 따라 일정하고** 가장자리로 갈수록 `1/cos`만큼 늘어난다.

#### 분해능 한계

도구가 읽는 각도는 존 중심으로 양자화되어 **±2.8°**다. 부호·전치 판정에는 충분하지만
`tof_fov_deg`를 한 번 재서 확정하기에는 부족하다(22.5°에 ±2.8°면 ±12%). FoV는
데이터시트 45°를 두고, RViz에서 알려진 장면과 눈에 띄게 어긋날 때만 손댄다.

#### D-3. 피치 — 바닥 행 적합으로 잰다

장착 규격은 피치 0°지만 브래킷이 조절식이 아니면 실측해서 싣는다. 바닥 행들이
그대로 측정기가 된다.

기울기를 하나 가정하고 **각 행이 함의하는 장착 높이**를 계산해, 행들이 한 값으로
모이고 그 값이 줄자로 잰 높이와 맞는 각도를 고른다. 관측이 넷이고 미지수가 둘이라
과결정이므로 우연히 맞을 수 없다.

```
h_행 = 바닥거리_행 x sin(공칭고도_행 + 기울기)
```

2026-08-06 좌측 센서 실측:

| 기울기 | row0 | row1 | row2 | row3 | 편차 |
|---|---|---|---|---|---|
| 0° | 61.7 | 60.3 | 53.4 | 34.2 | 27.5 |
| **3.0°** | **70.6** | **72.8** | **72.2** | **70.5** | **2.3** |
| 5° | 76.4 | 81.0 | 84.6 | 94.6 | 18.2 |

아래로 3.0°에서 네 행이 모이고 실측 70 mm와 일치한다.

**0이 아니면 두 곳에 넣는다.** 한쪽만 고치면 조용히 어긋난다.

| 어디 | 무엇 | 단위 |
|---|---|---|
| `sensors.yaml`의 `tof_pitch_deg` | 지면 필터가 바닥을 지울 때 | 도 |
| `sensor_usb.launch.py`의 `TOF_PITCH_RAD` | 반환점을 base_link 에 놓을 때 | 라디안 |

**왜 지면 필터가 피치를 알아야 하는가.** 수평이면 바닥 반사가 전부 z = −장착높이로
나와 한 임계값에 다 걸린다. 기울면 바닥이 프레임을 가로질러 기울어, 바닥을 가장
멀리 보는 축 근처 행이 임계값 위로 올라온다. 3° 기준 실측:

| 행 | 바닥 거리 | 계산되는 z | 피치 미반영 |
|---|---|---|---|
| −19.7° | 0.18 m | −0.062 | 걸림 |
| −8.4° | 0.36 m | −0.053 | 걸림 |
| **−2.8°** | **0.70 m** | **−0.034** | **통과 = 가짜 장애물** |

합성 프레임 검증에서 피치를 모르는 필터는 바닥 8점을 0.65~0.69 m에 남겼고, 피치를
반영하니 0점이 되면서 1 m 장애물은 그대로 살아남았다.

평벽 0.5 / 1.0 / 2.0 m. `tools/tof_probe.py`의 유효 존 중앙값이 ±5% 안이어야 한다.

### F. 자기 가림 마스킹

```bash
python3 tools/tof_mask_learn.py --topic /tof/left/points --seconds 10
```

앞을 비우고 **포크는 travel 높이로** 둔다. 리프트를 올리면 포크가 시야에서 빠지므로
높은 상태로 학습하면 주행 중에 놓친다. 출력된 목록을 `sensors.yaml`에 붙여넣고,

### G. 지면 반사

`tof_mount_height_m`에 실측값을 넣은 뒤, 바닥만 보이는 자세에서 발행 점이 0인지
확인한다. 겹이 두 개다 — 브리지의 높이 필터와 costmap의 `min_obstacle_height`.

### H. 크로스토크

두 센서가 같은 방향을 보므로 서로의 VCSEL 펄스를 잡을 수 있다.

1. 정면 20 cm에 평판
2. `config.h`의 `TOF_ENABLED_MASK`를 `0x1`로 빌드·플래시 → 좌측 거리 기록
3. `0x3`으로 되돌려 재측정 → 같은 존 비교

차이가 측정 반복도 이내면 문제없다. 크면 `task_tof.c`에 교대 레인징을 넣는다
(유효 주기가 7.5 Hz로 반감되지만 장애물 감지에는 충분).

### I. 모터 구동 중 EMI ← **가장 중요**

**정지 상태에서만 검증하고 넘어가면 안 된다.**

```bash
python3 tools/tof_probe.py 60
```

돌리는 동안 ① 스텝퍼 리프트를 상하로, ② 구동 모터를, ③ 둘을 동시에 움직이며
`@TFS`의 I2C 에러 카운터를 본다.

**정지 시 0이다가 모터를 켤 때 증가하면 EMI다.** 배선을 다시 정리한다 — I2C
배선을 스텝퍼 케이블과 분리, 교차는 직각으로, 스텝퍼 4선 꼬기, 센서 VIN 근처에
10~22 µF.

에러가 증가하면 브리지가 경고를 남긴다:

```
ToF left: I2C errors climbing 0 -> 14. If this only moves while the stepper
or drive motor runs, it is EMI on the sensor wiring
```

### J. TF·통합

```bash
ros2 run tf2_ros tf2_monitor odom base_link   # 발행 주체가 하나인지
rviz2                                          # Fixed Frame base_link
```

알려진 위치에 상자를 두고 PointCloud2가 그 위치에 찍히는지 본다. 그다음 낮은 상자가
local costmap에 marking되고 **LiDAR 장애물이 지워지지 않는지** 확인한다.

| 배선 재작업 | A·I |
| 바닥·타이어 변경 | 조향 중립 (`config.h` 주석의 실주행 절차) |

## 6. 브링업에서 배운 함정

같은 자리에서 다시 헤매지 않도록 기록한다. 자세한 것은
[펌웨어 README](../firmware/esp32/motor_controller/README.md)와
[tools/README](../firmware/esp32/motor_controller/tools/README.md).

| 증상 | 원인 |
|---|---|
| 실행마다 증상이 바뀜, 쓰기는 ACK인데 주소가 안 남음 | **`SPI_I2C_n` 플로팅** — 센서가 I2C/SPI 모드를 오감 |
| 주소 변경 직후 통신 두절 | `vl53l8cx_set_i2c_address()`가 마지막 쓰기를 **옛 핸들**로 보냄. `tof_change_address()`가 중간에 재바인딩 |
| LPn을 다시 내리면 주소 소실 | 주소가 통신 블록에 휘발성으로 저장됨. 한 번 깨운 센서는 계속 깨워 둔다 |
| 간헐 접촉·재부팅 | Y케이블 압착 분기점. 독립 배선으로 해결 |
| 회전 적분이 점점 줄어듦 | 바이어스 추적기가 회전을 흡수. 명령 기반 정지 판정만으로는 부족하고 **자이로 자체도 정지로 읽혀야** 한다 |
| ToF 초기화가 84KB 업로드에서 실패 | 짧은 트랜잭션은 통과하는데 긴 블록만 깨지는 것은 풀업 부족의 전형 |

**`vl53l8cx_set_i2c_address()`는 쓰지 않는다.** 이 ESP-IDF 포트에서 동작하지 않는
것을 실측으로 확인했다.

## 7. 지금 없는 것

### ESP32 자체 비상정지

계획서(`tof_integration_plan.md` §5)가 제안하지만 넣지 않았다.

- `task_motor.c`의 안전 경로를 직접 건드리는 변경이라 별도 검토가 필요하다
- Jetson이 `/safety_mode`를 내려보낼 새 UART 명령과 모드 상태기가 필요하다
- 이미 500 ms 텔레옵 워치독이 통신 두절을 덮고, 장애물 정지는 FR-304-2의 Nav2
  회피가 담당하도록 설계돼 있다

**넣는다면 필요한 것**: `@MODE` 명령, `task_motor.c`의 모드별 속도 상한, ToF 최소
거리 공유 경로, 그리고 모드 전환이 안전한지에 대한 리뷰.

### 구동 바퀴 엔코더

아직 없지만 **붙을 것을 전제로 구조를 잡아 뒀다.**

- 텔레메트리 프레임 규격이 `@IMU`/`@IMS`/`@TOF`/`@TFS`로 확장돼 왔고, `@ENC`가
  같은 방식으로 얹힌다. `frame_codec_wrap()`을 그대로 쓴다
- `sensor_protocol.py`의 `parse_sensor_line()`은 **모르는 종류를 거부하지 않고
  무시한다.** 펌웨어가 먼저 `@ENC`를 내보내도 구버전 브리지가 죽지 않는다
- `ekf.yaml`에 `odom1`로 바퀴 속도를 추가하면 된다. 지금 rf2o가 `vx, vy`,
  IMU가 `vyaw`를 담당하는 구조에 그대로 들어간다

엔코더는 IMU로 해결되지 않는 **정지 도킹 정밀도** 문제를 위한 것이다. 병진 속도
오차는 자이로가 줄여주지 않는다.
