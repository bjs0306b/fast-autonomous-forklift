# Nav2 장애물 대응 — 원인 분석과 조치

작성 2026-08-07 · 대상 브랜치 `feature/S15P11A304-52-fr-304-2-회피-경로-통합-현장-튜닝`

두 증상을 하나로 묶은 문서다. 같은 사건의 앞뒤이기 때문이다.

| 증상 | 내용 |
|---|---|
| **A** | 장애물을 만나면 회피하거나 경로를 다시 짜지 않고 **그 자리에 멈춘다** |
| **B** | 사라진 장애물이 지도에 **계속 남는다**. 사람이 비켜나도 안 지워진다 |

A 로 멈추고, B 때문에 영영 못 벗어난다.

**질문**: Nav2 의 한계인가, 코드의 미흡함인가. 소멸 기능은 따로 구현해야 하나.

---

## 0. 결론

**Nav2 의 한계가 아니다.** 필요한 기능이 전부 Nav2 안에 있는데, **꺼져 있거나
구조 때문에 동작하지 못했다.** 소멸도 따로 구현할 필요가 없다.

원인은 아홉 겹이고 전부 설정·코드 쪽이다.

| # | 원인 | 계층 | 조치 |
|---|---|---|---|
| 1 | BT 에 재계획 루프가 없다 | 대응 | ✅ 적용 |
| 2 | 플래너가 낮은 장애물을 못 본다 | 인식 | ✅ 적용 |
| 3 | SLAM 유령이 산술적으로 안 지워진다 | 인식 | ✅ 적용 |
| 4 | ToF 표시를 아무도 못 지운다 | 인식 | ✅ 적용 |
| 5 | 진행 판정이 정상 주행도 실패로 만든다 | 대응 | ✅ 적용 |
| 6 | 회전 능력이 각속도 상한에 묶여 있다 | 기동성 | ✅ 적용 (실차 확인 필요) |
| 7 | 가드의 회전 허용 문턱을 못 넘는다 | 기동성 | ✅ 적용 (실차 확인 필요) |
| 8 | 회피 조향이 2° 다 | 기동성 | ✅ 적용 (실차 확인 필요) |
| 9 | 시동 킥이 죽은 코드였다 | 기동성 | ✅ 적용 (실차 확인 필요) |

**증거**: `ros2_ws/tools/` 에 수동 탈출 스크립트 둘(`rear_recovery.py` 후진 탈출,
`left_recovery.py` 전진-좌 호)이 이미 있었다. Nav2 가 스스로 못 빠져나와 손으로
만든 우회책이다.

### 데모 직결이다

`docs/ros2/obstacle-avoidance-validation.md` — "동적 장애물은 빈 공간이 보여도
능동 우회하지 않는다."

설계상 동작은 **멈춤 → 비켜나기를 기다림 → 재개**다. 재개하려면 표시가 지워져야
하는데 안 지워졌다. 즉 **사람이 한 번 지나가면 영구 유령 벽이 생기고 차량은
재개하지 못했다.** RPP 가 `use_collision_detection: true` 로 costmap 을 보기
때문이다.

# 1부. 인식 — 장애물이 생기고 사라지는 것

## 1.1 Nav2 의 소멸 방식은 "광선 통과"다 — 시간이 아니다

이 구분이 전제다.

```
센서 →→→→→→→→ ▓ 장애물
     이 구간의 셀을 "비었다"로 지운다   ← raytrace clearing
```

**시간이 지나서 잊는 게 아니라, 그 자리를 다시 봐서 비어 있음을 확인해야 지운다.**
"다시 그 장소에 왔을 때 사라졌다고 인식" 이 정확히 이 동작이다.

설정은 관측원별 `clearing: True` 와 `raytrace_max_range` 다.

**stock Nav2 에 시간 기반 소멸은 없다.** `liblayers.so` 를 뒤져도 `voxel_decay`
같은 문자열이 없다. 그건 STVL 영역이다 (§4.3).

## 1.2 지도가 하나가 아니다

| 층 | 담는 것 | 소멸 방식 | 조치 전 |
|---|---|---|---|
| SLAM `/map` | 장기 기억, 벽 | Karto 누적 비율 | ❌ 산술적으로 불가능 |
| 글로벌 costmap | **플래너가 보는 것** | `ObstacleLayer` raytrace | ❌ ToF 미등록 |
| 로컬 costmap | 컨트롤러·가드가 보는 것 | `VoxelLayer` raytrace | ⚠️ LiDAR만 |

## 1.3 원인 3 — SLAM 유령

slam_toolbox 는 스캔이 지나간 횟수와 맞은 횟수를 **세션 시작부터 누적**해 비율로
판정한다.

```cpp
hitRatio = cellHitCnt / cellPassCnt;
*pCell = (hitRatio > occupancy_threshold) ? Occupied : Free;
```

| 임계값 | 히트 1회를 지우려면 |
|---|---|
| **0.1 (조치 전)** | **통과 10회** |
| **0.4 (조치 후)** | 통과 2.5회 |

사람이 3초만 서 있어도 10 Hz 스캔에 수십 번 히트가 쌓인다. 0.1 에서는 그 10배를
같은 2 cm 셀에 통과시켜야 했고, 2×3 m 경기장을 0.1 m/s 로 도는 한 세션 안에
**산술적으로 불가능**했다.

그리고 **Nav2 는 이걸 못 지운다.** `static_layer` 는 `/map` 을 덮어쓰기로
반영하고 그 위 `obstacle_layer` 는 최댓값으로 합쳐지므로, obstacle_layer 의
clearing 은 static 이 써 놓은 값 아래로 내려갈 수 없다. costmap 을 통째로 비워도
1초 뒤 다시 채워진다.

**조치**: `config/mapper_params_field.yaml` 의 `occupancy_threshold` 0.1 → **0.4**

> ⚠️ 올릴수록 약한 반사가 장애물로 안 찍힐 수 있다. 한 바퀴 돌려 벽이 제대로
> 그려지는지 확인하고 조정한다.

## 1.4 원인 4 — ToF 표시를 아무도 못 지웠다

```
nav2_params.yaml (조치 전)
# ToF 는 clearing: False 로 시작한다. 45도 원뿔이 공격적으로 clearing
# 하면 시야 가장자리 밖의 유효한 LiDAR 장애물을 지운다. 거동을 확인한
# 뒤에 좁은 raytrace 범위와 함께 켠다.
```

**"나중에 켠다"고 적어 두고 켜지 않았다.** 우려 자체는 타당했다. ToF 는
z=0.040 m, 화각 45°라 위쪽 광선이 멀리 갈수록 LiDAR 평면(z=0.202 m)을 침범한다.

| 센서 | 최상단 광선 | 침범 시작 |
|---|---|---|
| 좌 (아래로 3.0°) | +19.5° | 0.46 m |
| 우 (위로 1.1°) | +23.6° | 0.37 m |

### 조치 — 레이어를 나눴다

`combination_method` 가 설정돼 있지 않아 **기본값 1 (Maximum)** 이다. 레이어는
`max()` 로 합쳐지므로 **한 레이어의 "비었음"이 다른 레이어의 "막힘"을 지울 수
없다.**

```yaml
plugins: ["voxel_layer_lidar", "voxel_layer_tof", "inflation_layer"]
```

| | LiDAR 레이어 | ToF 레이어 |
|---|---|---|
| 관측원 | `scan` | `tof_left tof_right` |
| clearing | True | **True** ← 켤 수 있게 됨 |
| z 범위 | 0~0.80 m (16겹) | 0~0.40 m (8겹) |

ToF 광선이 z=0.20 을 지나며 지워도 그건 **ToF 레이어의 자기 격자**일 뿐이고
LiDAR 표시는 위 레이어에 있다. `raytrace_max_range` 를 0.35 m 로 조이는 대안보다
낫다 — 그러면 0.35 m 밖의 유령은 여전히 못 지운다.

## 1.5 원인 2 — 플래너가 낮은 장애물을 못 봤다

```
nav2_params.yaml (조치 전)
global_costmap > obstacle_layer > observation_sources: scan   ← ToF 없음
```

플래너는 **글로벌 costmap 위에서** 경로를 짠다. 낮은 상자는 ToF 만 보고, ToF 는
로컬에만 들어갔다. **ToF 를 단 이유 그 자체인 장애물을 플래너는 몰랐다.**

**이것 없이 재계획만 켜면 무한 루프가 된다** — 플래너가 같은 경로를 계속 다시
내고 컨트롤러가 계속 거부한다. 한 번 abort 하던 것이 영원히 도는 것으로 바뀔 뿐이다.

**조치**: 글로벌 costmap 에도 `voxel_layer_tof` 를 추가했다. 로컬과 같은 이유로
별도 레이어다.

# 2부. 대응 — 재계획과 복구

## 2.1 원인 1 — BT 에 재계획 루프가 없었다 (가장 큼)

조치 전 `navigate_to_pose_no_spin.xml` 전문이다.

```xml
<Sequence name="NavigateWithoutSpinRecovery">
  <ComputePathToPose goal="{goal}" path="{path}" planner_id="GridBased"/>
  <FollowPath path="{path}" controller_id="FollowPath"
              goal_checker_id="general_goal_checker"/>
</Sequence>
```

평범한 `Sequence` 다. **경로 계산이 딱 한 번 실행되고 끝난다.**

| | 조치 전 | Nav2 표준 |
|---|---|---|
| 최상위 | `Sequence` | `RecoveryNode(6)` |
| 주행 | 순차 | `PipelineSequence` |
| 경로 계산 | **1회** | `RateController hz=1.0` 로 계속 |
| 실패 | 즉시 abort | `ClearEntireCostmap` 후 재시도 |
| 복구 | 없음 | Spin / BackUp / Wait |

주석은 제자리 회전이 불가능해 `Spin` 을 뺐다고 설명한다. **그 판단은 옳다** — 이
차량에서 `Spin` 은 반드시 실패한다. 문제는 **재계획 루프까지 같이 버린 것**이다.
재계획은 `Spin` 과 아무 관계가 없다.

`bt_navigator` 의 `plugin_lib_names` 에 `RecoveryNode` · `RateController` ·
`ClearEntireCostmap` · `BackUp` 이 전부 등록돼 있었다. **쓸 수 있는데 안 썼다.**

**조치**: `behavior_trees/navigate_to_pose_replanning.xml` 신규.

```
RecoveryNode(6)
├─ PipelineSequence
│  ├─ RateController(1Hz) → RecoveryNode(1) → ComputePathToPose
│  │                                        └ ClearEntireCostmap(global)
│  └─ RecoveryNode(1) → FollowPath
│                     └ ClearEntireCostmap(local)
└─ ReactiveFallback
   ├─ GoalUpdated
   └─ RoundRobin
      ├─ ClearEntireCostmap(local + global)
      ├─ Wait(3)                    ← 사람은 움직인다. 기다리는 것도 복구다
      └─ BackUp(0.15, 0.08)
```

`Spin` 은 넣지 않았다. 두 런치(`nav2_forklift`, `field_slam_nav2`)를 새 트리로
연결했고, **옛 트리는 남겨 두었다** — 되돌릴 때 필요하다.

## 2.2 원인 5 — 진행 판정이 정상 주행도 실패로 만들었다

```
regulated_linear_scaling_min_speed: 0.04   → 0.5 m 에 12.5초
movement_time_allowance: 10.0              → 10초 안에 못 가면 abort
```

인플레이션 0.55 m 가 폭 2 m 경기장 전체를 덮어 비용 규제 감속이 상시 작동한다.
예외가 아니라 평시다. **제대로 움직이고 있어도 abort 됐다.**

**조치**: `movement_time_allowance` 10.0 → **25.0**

# 3부. 기동성 — 실제로 비켜날 수 있는가

여기부터는 주행 거동이 바뀐다. **실차 확인이 필요하다.**

## 3.1 원인 6 — 회전 능력이 각속도 상한에 묶여 있었다

`minimum_turning_radius: 0.54` 는 기계 한계(0.198 m)의 2.7배지만 **단순 실수가
아니었다.** `velocity_smoother` 의 각속도 상한이 그 값을 결정한다.

| 각속도 상한 | 조향각 | 실현 가능 반경 |
|---|---|---|
| **0.18 (조치 전)** | 14.5° | **0.556 m** |
| **0.40 (조치 후)** | 29.9° | **0.250 m** |
| 0.505 | 36.0° | 0.198 m (기계 한계) |

0.18 에서 실현 가능한 반경이 0.556 m 이므로 설정된 0.54 는 **오히려 컨트롤러가
추종할 수 없는 값**이었다.

그 결과 전진만으로 옆으로 비켜나는 데 필요한 거리가 이랬다.

| 반경 | 옆으로 0.30 m 이동에 필요한 전방 거리 |
|---|---|
| 0.54 (조치 전) | **0.48 m** |
| 0.198 (기계 한계) | 0.20 m |

**가드는 0.25 m 에서 멈춘다.** 멈춘 시점엔 이미 기하학적으로 회피가 불가능했다.

**조치**: 각속도 상한 0.18 → **0.40**, `minimum_turning_radius` 0.54 → **0.25**,
`regulated_linear_scaling_min_radius` 도 **0.25** 로 맞췄다.

> 마지막 항목을 빠뜨리면 계획된 모든 곡선에서 감속이 걸리고, 그 속도는 실측
> 스톨 구간이라 차가 아예 멎는다.

## 3.2 원인 7 — 가드의 회전 문턱을 못 넘었다

가드가 좌/우로 틀려면 그쪽 라이다 통로가 `minimum_turn_clearance_m` 이상 비어
있어야 한다.

| 주행 레인 | 벽까지 여유 | 0.55 기준 |
|---|---|---|
| x = 0.50 | 0.426 m | 미달 |
| x = 1.55 | 0.376 m | 미달 |

**폭 2 m 경기장에서는 어느 지점에서도 통과할 수 없었다.** `_choose_turn` 이 항상
`SLOW, yaw_bias = 0.0` 을 돌려주었다 — 가드는 애초에 조향할 수 없는 상태였다.

**조치**: 0.55 → **0.30**

## 3.3 원인 8 — 회피 조향이 2° 였다

```
0.02 rad/s ÷ 0.08 m/s        = 곡률 0.25 1/m
후륜 조향 atan(0.144 × 0.25) = 2.06°      (기계 한계 36% 의 5.7%)
회전반경                      = 4.0 m
```

회피가 아니라 **미세 보정**이었다. 0.25~1.00 m 구간을 9.4초에 지나며 얻는 헤딩
변화가 10.8° 뿐이다.

**조치**: `avoidance_yaw_rate_rps` 0.02 → **0.15** (후륜 15.1°, 반경 0.53 m)

## 3.4 원인 9 — 시동 킥이 죽은 코드였다

`ForwardStartupKick` 클래스와 `forward_startup_kick_*` 설정이 예전부터 있었는데
**아무도 만들지 않아 한 번도 동작한 적이 없었다.**

실측 마찰표(`config/teleop.yaml`)와 Nav2 명령을 대조하면:

| Nav2 상황 | 속도 | 구동 % | 실측 판정 |
|---|---|---|---|
| 순항 | 0.10 | 48% | 출발 문턱 50% 미만 |
| 가드 감속 | 0.08 | 45% | 자력 출발 불가 |
| 곡률 규제 하한 | 0.04 | 40% | **반반** |
| 목표 접근 | 0.03 | 39% | **스톨** |

**킥 없이는 정지에서 출발 자체를 못 한다.** 재계획이 되더라도 움직이지 않는다.

그리고 **후진은 킥이 아예 없었다.** 기존 구현은 `drive_percent <= 0` 이면 킥을
취소한다. 2.1 의 `BackUp` 복구는 정지 상태에서 후진을 명령하므로 그대로 두면
**복구 동작이 그냥 안 움직인다.**

**조치**: `ForwardStartupKick` → `StartupKick` 으로 일반화해 브리지에 배선했다.

- 방향(정지/전진/후진)을 추적, **0 또는 반대 방향에서 진입할 때** 킥
- 전진 50% · **후진 100%** (조향된 후진 실측 근거)
- 정지 명령은 즉시 취소 — 가드의 정지 권한 유지

## 3.5 그리고 구동 퍼센트가 기동을 막고 있었다

작업 트리의 `teleop.yaml` 이 `min 18 / max 45`, 킥은 50 이었다.

```
min <= kick <= max   →   18 <= 50 <= 45   →   거짓   →   ValueError
```

**다음 `colcon build` 에 `uart_teleop_bridge` 가 생성자에서 죽는다.** `install/`
이 옛 값이라 가려져 있었을 뿐이다. 게다가 18/45 면 Nav2 순항이 32% — 실측
"못 구름" 구간이다.

**조치**: 35 / 60 으로 원복. 왜 그 범위여야 하는지를 설정 주석에 남겼다.

# 4부. 적용하지 않은 것

## 4.1 REEDS_SHEPP + `allow_reversing: true`

플래너가 후진 구간을 만들면 경로에 **커스프(방향 전환점)** 가 생기고, 매
커스프마다 정지마찰을 다시 이겨야 한다. 3.4 의 후진 킥이 **실차에서 검증된 뒤에**
켜는 것이 맞다. `BackUp` 복구만으로도 교착 탈출은 된다.

## 4.2 STVL (시간 기반 소멸)

`spatio_temporal_voxel_layer` 는 `voxel_decay` 로 "N 초 뒤 자동 소멸"을 준다.
**미설치**이고 apt 후보는 있다(2.3.4-1jammy).

권하지 않는 이유:
- 재방문 raytrace 로 충분하다. 경기장이 작아 금방 다시 본다
- 새 패키지 도입은 데모 3일 전에 질 위험이 크다
- 레이어 교체라 파라미터를 처음부터 다시 맞춰야 한다

다만 **차량이 그 자리를 다시 볼 수 없는 경우**(뒤쪽에 생긴 장애물)에는 시간
소멸이 유일한 해법이다. 데모 이후 과제.

## 4.3 정지 시 조향 유지

`mapping.py:140` 의 데드밴드는 정지 명령이 오면 구동 0 **그리고 조향을 중립으로**
되돌린다. 후륜 조향차는 정지 상태에서 방향을 못 바꾸므로 STOP 이 자기 유지
상태가 된다.

고치면 재출발 시 곧바로 호를 그릴 수 있지만, **정지 상태에서 서보를 돌리는 것은
부하가 크다.** 효과 대비 위험이 커서 제외했다.

# 5부. 검증

## 5.1 인식

| # | 확인 | 합격 |
|---|---|---|
| 1 | 낮은 상자를 앞에 두기 | 로컬·**글로벌** costmap 에 찍힘 |
| 2 | **상자를 치우고 그 자리를 다시 보기** | **표시가 사라짐** ← 핵심 |
| 3 | ToF clearing 을 켠 뒤 | **LiDAR 가 찍은 벽이 안 지워짐** (역검증) |
| 4 | 한 바퀴 주행 후 `/map` | 벽이 제대로, 유령 없이 |

**3번을 빠뜨리지 말 것.** ToF clearing 을 켜는 것의 위험이 바로 그것이고, 레이어
분리가 막아준다는 것을 실제로 확인해야 한다.

## 5.2 대응

| # | 확인 | 합격 |
|---|---|---|
| 5 | `ComputePathToPose` 호출 빈도 | 1 Hz 로 반복 |
| 6 | 장애물 앞에서 멈춘 뒤 | 재계획이 일어남 |
| 7 | 장애물을 치우면 | 주행이 재개됨 |

## 5.3 기동성

| # | 확인 | 합격 |
|---|---|---|
| 8 | `BackUp` 복구 | 실제로 물러남 (후진 킥) |
| 9 | 좁은 통로 | 회피 조향이 실제로 걸림 |
| 10 | 곡선 추종 | 횡오차가 커지지 않음 |
| 11 | 정지에서 출발 | 자력으로 출발함 (전진 킥) |

## 5.4 진단 함정

**`/obstacle_avoidance/status` 가 조용하면 가드가 원인이 아니다.** 가드는
`/cmd_vel` 이 0.5초 끊기면 상태 발행도 같이 멈춘다. 조용한 것은 **Nav2 가
포기했다는 신호**다.

## 5.5 되돌리는 법

각 단계가 독립 커밋이다. 실차에서 문제가 생기면 그 단계만 되돌린다.

기동성(3부)이 불안하면 BT 를 옛 트리로 되돌리지 말고 **3부만** 되돌리는 편이
낫다 — 재계획·복구(2부)와 인식(1부)은 거동을 바꾸지 않는다.
