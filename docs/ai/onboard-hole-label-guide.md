# 온보드 포크 정렬 — `hole` 라벨 가이드

> 대상: S15P11A304-144 미니어처 데이터셋 촬영·라벨링 (온보드 -s 포크 정렬 비전용)
> 확정일: 2026-07-29 · 관련: 145(파인튜닝) · 152(정렬 제어 루프) · 153(블라인드 진입) · 154(성공·실패 판정)

## 1. 왜 클래스로 검출하나

포크 정렬 사다리의 **Level 2를 고전 CV가 아니라 학습 클래스로** 간다.

- 고전 CV로 파렛트를 다루려던 시도는 이미 실패했다 — `pallet_autolabel` 최고 7/40, 가림 상황에서 무력.
- 검은 플라스틱 파렛트의 구멍은 **명암 대비가 낮아** 임계·에지 기반이 특히 불리하다. 구멍 안쪽이 어둡고 파렛트 본체도 어둡다.
- 어차피 이 촬영분으로 온보드 -s를 파인튜닝하므로 **클래스 하나 늘리는 한계비용은 라벨링뿐**이다.

사다리: bbox 역산(L1) → **구멍 검출 클래스(L2, 채택)** → 키포인트(L3) → ArUco(L4)

⚠️ **클래스 구성은 배포처별로 다르다.** 온보드 -s는 **`pallet`·`hole`**, 스테이션 -m은 **`box`·`pallet`** — 둘 다 2클래스지만 **구성이 다르다**. 스테이션은 구멍을 볼 이유가 없고, 현역 exp8 계보를 건드리면 검증 끝난 치수(0.66mm)·편하중 KPI를 다시 태워야 한다.

> **온보드 `box` 폐기 (2026-07-30)**: 당초 온보드를 3클래스(box·pallet·hole)로 계획했으나,
> exp8 프리라벨이 흰 파렛트를 box로 오인해(장당 2.4개, 파렛트 오인 22%) pallet 검출(G2)을
> 해쳐서 **box를 뺐다.** `onboard_eval.json` 어노테이션도 `pallet 105` · `hole 221` ·
> **box 0건**이다. `label_onboard.py`의 `CLASSES`에 box(id 1)가 슬롯으로 남아 있지만
> 비어 있다 — 이 잔재 때문에 "3클래스" 기술이 문서에 남아 있었다(2026-08-03 정정).

## 2. 실측 치수 (2026-07-29)

| 항목 | 값 | 비고 |
|---|---|---|
| 미니 파렛트 | 110 × 110 × **14** mm | 높이는 실측. SCAD 기본값(12mm)은 미검증 표준 근사치였다 |
| **개구부(구멍)** | **35 × 9.5 mm** | 종횡비 약 **3.7 : 1** — 납작하다 |
| 통로 중심 간격 | **48~49 mm** | |
| 포크 | 두께 **5 mm**(뿌리) · 너비 **12 mm** | 끝으로 갈수록 얇아지는 **테이퍼** |

**여유가 가로·세로에서 5배 차이 난다.**

- 가로: (35 − 12) / 2 = **±11.5 mm**
- 세로: (9.5 − 5) / 2 = **±2.25 mm** ← 뿌리 기준, 테이퍼라 진입 시작은 더 넉넉

→ **비전(`hole`)은 가로 x와 요(yaw)를 책임진다.** 높이(세로)는 ±2.25mm라 카메라로 잡기엔 비싸고, **스텝모터 캘리브레이션 + 리밋 스위치**(FR-303-4)가 담당하는 것이 맞다.
→ 테이퍼는 **153(블라인드 구간 오픈루프 진입)의 물리적 근거**다. 끝을 걸치고 밀어 넣으면 상하로 자기정렬된다.

## 3. 라벨 규약

### ① 구멍 하나가 인스턴스 하나 — 묶지 않는다

포크가 2개고, 정렬은 두 구멍 중심선에 두 포크를 맞추는 문제다. 하나로 묶으면 중심은 알아도 **간격을 모른다.** 더 중요한 건 비스듬히 볼 때 **먼 쪽 구멍이 좁게 보이는 폭 비가 요(yaw) 신호**라는 점이다 — 묶으면 사라진다.

### ② modal — 보이는 대로 그린다 (파렛트의 amodal 규약을 따르지 않는다)

클래스마다 규약이 다른 이유는 **하류가 묻는 질문이 다르기 때문**이다.

| 클래스 | 규약 | 하류가 묻는 것 |
|---|---|---|
| `pallet` | **amodal** (가려진 부분까지 전체 범위) | 파렛트의 실제 중심·상단은 어디인가 (편하중·on_pallet·tilt) |
| `box` | modal | 보이는 화물은 어디 있나 |
| `hole` | **modal** | **여기에 포크를 꽂을 수 있나** |

가려진 구멍은 꽂을 수 없다. amodal로 그리면 화물이나 다른 파렛트에 막힌 구멍도 "열려 있다"고 가르치게 되고, 그 대가는 **포크가 박는 것**이다. 비용이 비대칭이므로 modal이 맞다.

### ③ 가로가 원래의 50% 미만으로 보이면 라벨하지 않는다

35mm × 50% = 17.5mm이고 포크 너비가 12mm다. 즉 **50%가 "여유 5.5mm 남은 진입 한계선"** 이라 경계로서 자연스럽다. 그 이하는 진입 대상이 아니므로 가르치지 않는다.

완전히 안 보이면 당연히 라벨 없음. 단 **`pallet`은 그대로 amodal로 그린다**(기존 규약 유지).

**화면 밖으로 잘린 파렛트는 예외다** — amodal은 *가려진* 부분을 채우는 규약이고, 프레임 경계는 가림이 아니다. COCO bbox는 이미지 좌표를 벗어날 수 없으므로 **경계에서 자른다**. 실제로 구간 5의 프레임 214는 파렛트가 오른쪽 화면 끝에서 잘려 있다. 온보드에서는 손실이 없다 — 잘린 파렛트는 접근 대상이 아니고, 진입면 선택은 보이는 구멍으로 하기 때문이다(§3-⑥). 파렛트의 실제 중심을 요구하는 하류(편하중)는 **스테이션 -m 쪽 관심사**이고 거기엔 이 규약이 적용되지 않는다.

### ④ 크기 하한은 **세로** 기준 — 원본 16px 미만 제외

종횡비가 3.7:1이라 **세로가 먼저 뭉개진다.** 가로 20px로 자르면 세로가 5px밖에 안 돼 RTMDet-s(최소 stride 8)에서 학습이 안 된다.

> 개구부 **세로가 원본(1280×800)에서 16px 미만**이면 라벨하지 않는다 (640 환산 8px).

이때 가로는 약 59px, 파렛트 전체는 약 185px이다. 포크 접근 뷰에서는 파렛트가 이보다 훨씬 크게 잡히므로 실촬영에 제약이 되지 않는다. 이 프레임은 `pallet`만 라벨한다.

### ⑤ 경계는 구조물 기준 — 그림자가 아니다

구멍은 어두워 경계가 번져 보인다. **상판 아랫면 ~ 하판 윗면, 좌우 다리 안쪽 면**이 만드는 실제 개구 사각형을 따른다. 그림자가 안쪽으로 퍼져 보여도 구조를 기준으로 그린다.

### ⑥ 비스듬히 볼 때 보이는 구멍은 **전부** 그린다

파렛트는 다리가 3×3이라 **네 면 모두 포크가 들어가고, 각 면에 구멍이 2개**씩 있다. 정면(0°)에서는 앞면 2개만 보이지만 **회전 45° 부근에서는 옆면 구멍까지 화면에 잡혀 최대 4개**가 된다. 촬영 변형 축에 회전 0~45°가 있으므로 이런 프레임이 다수 나온다.

**보이는 것을 전부 그린다.** 앞면 2개만 그리는 방식은 채택하지 않았다 —

> 그 방식은 라벨러에게 **사진만 봐서는 알 수 없는 것**을 요구한다. 어느 면으로 진입할지는 지게차가 어느 방향에서 접근하느냐에 달렸고, 그건 정지된 사진에 없는 정보다. 45° 근처에서 사람마다 다르게 판단하면 모델은 "어떤 구멍은 구멍이 아니다"라는 모순된 신호를 배운다.

대신 진입면 선택은 **런타임에** 한다(152): **두 구멍의 중심을 이은 선분이 더 길고 개구가 넓은 쪽**을 진입면으로 고른다. 정면에 가까울수록 구멍이 넓게 보이기 때문이다.

## 4. 클래스 id와 검수

```
box = 1, pallet = 2, hole = 3
```

기존 계보(box=1, pallet=2)를 유지하고 뒤에 붙인다.

**검수 자동 체크** — 라벨 검수기에 넣을 sanity check:

1. `hole` bbox는 **`pallet` bbox 안에 포함**돼야 한다
2. `hole` 종횡비가 1.5:1 미만이면 경고 (정상은 약 3.7:1, 너무 정사각이면 오라벨 의심)
3. 한 프레임의 `hole` 개수가 **5개 이상이면 경고** (구조상 최대 4개)
4. `pallet`이 없는데 `hole`만 있으면 오류

## 5. 카메라 설치 (2026-07-29 실측)

**해상도는 1280×800이 최대다.** 판매 스펙의 1280×960은 나오지 않는다 — 요청해도 조용히 800으로 떨어진다. 지원 모드는 640×480 · 800×600 · 1280×720 · **1280×800**(30fps). 노트북에서는 index 1이다(index 0은 내장 웹캠).

**내려다보는 각(θ)을 20° 이하로.** 구멍은 지면에서 2.25~11.75mm 구간의 얇은 슬롯이라, 위에서 내려다보면 개구가 `9.5 × cosθ`로 납작해진다.

| θ | 화면상 개구 높이 |
|---|---|
| 20° | 8.9mm (−6%) |
| 30° | 8.2mm (−13%) |
| 45° | 6.7mm (−29%) |

납작해질수록 §3-④의 세로 16px 하한에 먼저 걸린다. **카메라는 낮게, 광축은 수평에 가깝게** 단다. 높이 6cm면 거리 15cm에서 21°, 높이 12cm면 30cm에서 20°다.

**뒤집어 장착했다면 `--rotate180`을 쓴다.** 뒤집힌 채로 찍으면 ①사람이 뒤집힌 화면을 보고 라벨해야 하고 ②정립으로 라벨된 공개 데이터(LOCO `pallet`)와 방향이 어긋나며 ③"화물은 파렛트 위에 얹힌다" 같은 하류 기하 가정이 반대가 된다.

> ⚠️ **추론 경로에도 같은 회전을 넣어야 한다.** 한쪽만 돌리면 학습·추론 도메인이 정반대가 되고, 모델이 아무것도 못 잡는데 원인을 찾기 어려운 상태가 된다.

```
python src/station/shoot.py --out data/raw/onboard/train_20260729/b01 \
    --prefix onb --camera 1 --width 1280 --height 800 --rotate180 --burst 6
```

## 6. 촬영·라벨 체크리스트

- [ ] 뷰: **포크 접근 뷰(낮은 정면)** — 온보드 카메라 실제 장착 위치·높이 그대로
- [ ] train(300~500장)과 eval(100~150장)을 **촬영 단계부터 분리** (딴 날·딴 배치, 누수 차단)
- [ ] 변형 축: 위치(중앙/편심), **회전 0~45°**, 조명 3종, 배경 변형, 네거티브(빈 바닥·파렛트만)
- [ ] 프리라벨은 기존 -s로 `box`·`pallet`만. **`hole`은 사람이 처음부터 그린다** (모델이 모르는 클래스라 프리라벨이 없다)
- [ ] eval 셋은 최종 평가 전까지 열지 않는다

## 7. 알려진 한계

- 세로 여유 ±2.25mm는 **뿌리 기준**이다. 테이퍼 형상이 `pallet_mini.scad`에 모델링돼 있지 않아, 진입 초기의 실제 여유는 도면이 아니라 실물로만 확인된다.
- 다리 블록 치수(13.3mm)는 직접 잰 값이 아니라 **개구 폭 35mm·중심 간격 48~49mm에서 역산**한 값이다. 세 숫자가 서로 맞아떨어져 신뢰할 만하지만, 재출력 전에는 블록을 직접 재보는 것이 안전하다.
