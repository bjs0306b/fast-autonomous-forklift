# 온보드 포크 정렬 — 타깃 선택 규칙과 오차 정의

> 확정일: 2026-07-31 · 대상: S15P11A304-143(오차 산출) → 152(제어 루프)
> 구현: `ai/src/perception/fork_align.py` · 채점: `ai/scripts/eval_entry_face.py`
> 선행 문서: `onboard-hole-label-guide.md`(라벨 규약) · `onboard-tensorrt-runbook.md`(성능)
>
> **이 문서는 설계 근거다. 실물에서 돌리는 절차는 `onboard-fork-align-runbook.md`.**

152 제어 루프를 짜기 전에 **"어느 파렛트의 어느 면으로 갈지"** 를 먼저 정한다. 이걸
정하지 않으면 프레임마다 다른 대상을 쫓아 제어가 발산한다.

## 0. 왜 이게 선결 문제인가

2026-07-31 젯슨 라이브에서 **창밖 흰 건물이 `pallet 0.50`으로 잡혔다.** 임계 0.7로
걸리긴 했지만, 진짜 창고에서는 **진짜 파렛트가 여럿 보인다** — 그때는 임계로 못 거른다.
검출기는 "파렛트가 여기 있다"까지만 말하고 "어디로 가라"는 말하지 않는다.

## 1. 파렛트 선택 — 자격과 순위를 나눈다

### 자격: 진입면이 있어야 한다

**구멍이 2개 미만인 파렛트는 score가 아무리 높아도 버린다.** 꽂을 구멍이 안 보이면
정렬할 대상이 아니다.

덤으로 오탐이 한 겹 더 걸린다. 창밖 건물·커튼 같은 도메인 밖 오탐은 그 안에 `hole`이
없다. `filter_by_geometry`(파렛트 밖 hole 제거)와 **방향이 반대이면서 맞물린다** —
한쪽은 파렛트로 구멍을 거르고, 이쪽은 구멍으로 파렛트를 거른다.

| 방어선 | 무엇을 거르나 | 근거 |
|---|---|---|
| pallet 임계 0.7 | 흰 커튼·건물 pallet 오탐 | 재현율 손실 0, 네거티브 19.5%→0% |
| `filter_by_geometry` | 파렛트 밖 hole 오탐(창문 격자) | 기하, 재현율 손실 0 |
| **자격(구멍 2개)** | **구멍 없는 파렛트 오탐** | 진입 불가능한 대상 |

### 순위: 진입면 점수를 그대로 쓴다

**선분 길이 × 최소 개구폭** 하나로 정한다. "가까운 것"·"화면 중앙" 같은 기준을 따로
만들지 않았다 — 그 점수가 이미 둘을 담고 있기 때문이다:

- 가까울수록 두 구멍의 화면 간격이 크다 (길이↑)
- 정면일수록 개구가 넓다 (폭↑) — 옆으로 비껴 있으면 폭이 먼저 깎인다

> ⚠️ **이 순위는 실측으로 검증되지 않았다.** eval 150장은 파렛트가 **전 프레임 정확히
> 1개**라(105/105) 여러 개 중 고르는 상황이 데이터에 아예 없다. 다중 파렛트 프레임을
> 찍기 전까지는 **설계 근거만 있는 규칙**이다. (검증 방법: 파렛트 2~3개를 거리·각도를
> 달리해 놓고 촬영 → 사람이 "접근 대상"을 표시 → 규칙 일치율)

### 락과 히스테리시스 — 매 프레임 argmax는 금지

점수가 붙는 상황이 실제로 흔하다(§2). 프레임마다 argmax를 다시 뽑으면 22fps 제어가
좌우로 떤다. 그래서:

- **히스테리시스**: 새 후보가 현재 타깃의 **1.3배**를 넘어야 갈아탄다. 붙는 구간
  (≤1.2배)보다 위, 실제로 갈아탈 만한 차이(eval 중앙값 1.50배)보다 아래다.
- **유예 5프레임**(≈0.23초): 검출이 깜빡여도 락을 유지한다. 놓친 프레임마다
  상태기계를 되돌리면 진입이 끊긴다.
- 프레임 간 동일 파렛트 식별은 **IoU ≥0.3**(위치 연속성). score로 잇지 않는다 —
  score는 프레임마다 흔들린다.

락 해제는 152 상태기계의 몫이다(`TargetTracker.reset()`).

## 2. 진입면 선택 — 규약을 그대로 옮기면 틀린다

라벨 가이드 §3-⑥이 런타임에 미뤄둔 문장: *"두 구멍의 중심을 이은 선분이 더 길고
개구가 넓은 쪽"*. **이걸 문자 그대로 구현하면 전부 틀린다.**

train·eval의 다면 프레임 47장(구멍 3개 이상 = 두 면이 동시에 보임)으로 채점했다:

| 후보 | train 40장 | eval 7장 | 마진 중앙값(train/eval) |
|---|---|---|---|
| 전체 쌍 · 거리만 | 0/40 | 0/7 | — |
| 전체 쌍 · 거리×평균폭 | 1/40 | 0/7 | 1.09 / 1.10 |
| 인접 쌍 · 거리×평균폭 | 33/40 | 7/7 | 1.62 / 1.09 |
| **인접 쌍 · 거리×최소폭** ← 채택 | **33/40** | **7/7** | **1.90 / 1.50** |

### ① 인접 쌍 제한이 결정적이다 (0/40 → 33/40)

앞면 구멍과 옆면 구멍을 하나씩 집으면 **선분이 가장 길어진다.** "가장 긴 쪽"을 그대로
고르면 반드시 오답이 된다. 파렛트는 볼록하고 두 면은 모서리를 공유하므로 **각 면의
구멍은 화면 x에서 겹치지 않는 구간**을 차지한다 → x로 정렬하면 같은 면끼리 이웃한다.

### ② 폭은 평균이 아니라 최소

정답률은 같고 **1등/2등 여유가 벌어진다**(중앙값 train 1.62→1.90, eval 1.09→1.50).
물리적으로도 최소가 맞다 — **포크는 둘 다 들어가야 하므로 좁은 쪽 개구가 제약**이다.

### 남은 불일치 7장은 오답이 아니다

전부 **45° 부근**이고 두 면의 개구가 112~124px 대 126~142px이다. 어느 쪽으로 들어가도
되는 프레임이라, 거기서 갈리는 건 규칙이 아니라 임의의 타이브레이크다.

⚠️ 다만 그 구간에서 **최소폭 쪽 마진 최솟값이 train 1.14 → 1.00배로 되레 붙는다.**
손해는 아니지만 **매 프레임 argmax를 그대로 쓰면 면이 뒤집힌다**는 신호다 — §1의
히스테리시스가 그래서 필요하다.

## 3. 정렬 오차 정의 — 전부 화면 단위

내부 파라미터(초점거리) 없이 계산된다. 152의 P 제어는 이 셋이면 닫힌다.

| 값 | 정의 | 부호 |
|---|---|---|
| `lateral_ratio` | (진입면 중심 x − 포크 중심선 x) / (진입면 폭의 절반) | +면 파렛트가 오른쪽 |
| `yaw_signal` | (왼쪽 구멍 폭 − 오른쪽 구멍 폭) / (두 폭의 합) | +면 오른쪽 끝이 더 멀다 |
| `approach_px` | 두 구멍 중심 간 화면 거리 | 클수록 가깝다 |

- **좌우를 비율로 재는 것**은 `load_balance`가 편하중에서 쓴 방식 그대로다 — 픽셀→mm
  캘리브레이션 없이 동작하고, 거리가 변해도 같은 임계를 쓴다.
- **요를 폭 비로 재는 것**은 라벨 규약 §3-①이 "구멍을 묶지 말라"고 한 바로 그 이유다:
  두 구멍의 실제 폭은 같으므로(35mm) 화면 폭 비가 곧 깊이 비다(w₁/w₂ = d₂/d₁).
- **포크 중심선**(`fork_center_x`)은 기본이 이미지 중앙이지만, 카메라를 차체 중심에서
  벗어나게 달았다면 반드시 넣는다. **장착 오프셋을 여기서 흡수하지 않으면 제어가 일정한
  편차를 안고 수렴한다.**

### 절대 단위가 필요하면 초점거리를 준다

`focal_px`를 주면 `yaw_deg`·`distance_mm`이 나온다. 유도:

```
w₁/w₂ = d₂/d₁                     (두 구멍의 실제 폭이 같다)
→ (d₂−d₁)/(d₂+d₁) = yaw_signal
Δd = S·sinθ,  d̄ = f·S·cosθ / span  (S = 통로 중심 간격 48.5mm)
→ tanθ = 2f/span · yaw_signal      (S가 약분돼 사라진다)
```

S가 약분되므로 **간격 실측 오차에 둔감**하다. 대신 `f`가 필요하다.

> ✅ **카메라 캘리브레이션 완료**(2026-07-31, S15P11A304-176 · `fx = 1277.65`).
> 절차는 `docs/ai/measurement/camera-calibration.md` §2. 이제 요각을 도 단위로
> 낼 수 있어 진입 판정에 `--yaw-deg-tolerance`(기본 10°)를 쓴다.
>
> ⚠️ 다만 제어 루프의 조향 입력은 여전히 `yaw_signal`(무차원)이다. 큰 각도에서
> 포화되므로 **판정에는 쓰지 않는다** — 실제로 -58.5°가 -0.07로 나와 진입이
> 허가된 적이 있다(2026-08-05).

## 4. 제어 루프 (152)

구현 `ai/src/control/fork_servo.py` · 노드 `ai/scripts/onboard_fork_align_node.py`

### 상태기계 — 순서를 강제한다

```
SEARCH ──타깃 획득──> APPROACH ──근접──> ALIGN ──진입 거리──> VERIFY ──정렬됨──> INSERT ──> DONE
   ^                     |                |                    |                  (개루프)
   └──── 소실 ───────────┴────────────────┘                    └─미정렬─> RETREAT ─> APPROACH ...
                                                                              └─ 재시도 소진 ──> ABORT
```

**뒷바퀴 조향은 제자리 회전이 안 된다.** 파렛트 코앞에서 요각을 고칠 수 없으므로
진입 전에 정렬을 끝내야 한다. 그래서 진입 거리(`INSERT_ENTER_PX`)에 도달했을 때
정렬이 안 돼 있으면 **그 자리에서 고치려 들지 않는다** — 틀어진 만큼 물러났다가
다시 접근한다.

> **2026-08-05 갱신 — 154 재시도가 구현됐다.** 설계 당시에는 "미정렬이면 즉시
> ABORT, 재접근은 154에서"였으나 지금은 `VERIFY`·`RETREAT` 두 단계가 들어가
> 같은 루프 안에서 재접근한다(기본 `--max-retries 20`, 0이면 종전처럼 즉시 ABORT).
> 45°로 돌아간 파렛트에 재접근 9회로 관통한 것이 이 경로다.
> 단계별 근거·플래그는 `docs/ai/onboard-fork-align-runbook.md` §5-2.

**INSERT는 래치된다.** 코앞에서는 구멍이 화면 밖으로 나가 검출이 끊기는 것이 정상이다.
들어가기로 했으면 눈을 감고 직진한다(153 블라인드 진입). 포크 테이퍼가 상하 자기정렬을
해주는 것이 물리적 근거다.

### 조향 부호 — 두 항의 부호가 같다

카메라 원점, 전방 +Y, 오른쪽 +X. 파렛트 면이 반시계로 θ 돌면 오른쪽 구멍이 멀어져
좁게 보인다(`yaw_signal > 0`). 그때 면의 바깥 법선은 `(+sinθ, −cosθ)` — **우리 기준
오른쪽**을 향한다. 그 법선 위로 올라가려면 오른쪽으로 돌아 들어가야 한다.
좌우 오차도 같은 방향이므로:

```
angular_z = −(k_lat · lateral_ratio + k_yaw · yaw_signal)     (ROS 관례: +z = 좌회전)
```

⚠️ **두 항을 더하면 균형점에 수렴할 뿐 둘 다 0이 되지는 않는다.** 그래서 ALIGN에서
요 게인에 `ALIGN_YAW_BOOST`(2.0)를 곱해 **요를 먼저 죽인다** — 좌우는 진입 직전까지
볼 수 있지만 요는 코앞에서 못 고치기 때문이다.

### ⚠️ 게인·임계는 전부 미조정 자리표시자다

실물 없이 정할 수 없다(장착 높이·각도, 슬립, 서보 응답). 지금 값은 **부호와 구조가
맞는지 보기 위한 것**이지 현장 값이 아니다. `ALIGN_ENTER_PX`·`INSERT_ENTER_PX`는
카메라·해상도에 종속이라 특히 그렇다.

### 안전

- 어떤 경로로 끝나든(예외·Ctrl-C 포함) **0 Twist를 낸다.** 브리지 워치독(500ms)이
  잡아주긴 하지만 그 사이에 들이받기 충분하다.
- 정지 상태에서도 0 Twist를 계속 낸다 — 안 내면 워치독 정지와 의도한 정지가 구분되지
  않는다.
- **첫 실행은 `--dry-run`.** 부호가 반대면 지게차가 파렛트로 돌진한다.

### 에피소드 로깅

정렬 시도마다 `(시각, 오차, 명령)`을 남긴다. 154의 성공·실패 판정 근거로 어차피 필요한
데이터라 추가 비용이 없고, 나중에 모방학습을 붙일 여지를 닫지 않는다.

> **강화학습을 쓰지 않는 이유**: 이 문제는 "상태 → 동작"의 관계가 기하로 정확히
> 계산된다. RL은 그 관계를 모를 때 시행착오로 알아내는 방법이라 아는 것을 다시 배우는
> 셈이 된다. 학습 비용(수천 회 시도)도 스프린트에 맞지 않고, 시뮬레이터로 우회하면 이
> 프로젝트가 세 번 데인 도메인 갭을 또 만난다. 마지막 진입은 테이퍼가 물리적으로
> 해결하므로 학습할 것도 없다.
