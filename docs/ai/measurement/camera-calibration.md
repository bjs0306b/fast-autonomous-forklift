# 카메라 캘리브레이션

카메라가 둘이고 **쓰는 축이 다르다.** 헷갈리지 말 것.

| | 스테이션 (BRIO) | 온보드 (Jetson USB) |
|---|---|---|
| 용도 | 화물 치수·적재 높이 | 포크 정렬 요각·거리 |
| 해상도 | 1920×1080 | 1280×720 |
| **쓰는 값** | **`fy` = 2039.07** (세로) | **`fx` = 1277.65** (가로) |

축이 다른 이유: 스테이션은 **적재 높이**(세로)를 재고, 온보드는 **가로로 놓인 구멍 두 개**의
간격을 본다(`tanθ = 2f/span · yaw_signal`의 span이 가로 픽셀 거리).

---

# 1. 스테이션 (Logitech BRIO 100)

## 사용 장비

- 카메라: Logitech BRIO 100
- 촬영 해상도: 1920 × 1080
- 체커보드 내부 코너: 9 × 6
- 체커보드 한 칸 크기: 24 mm

## 카메라 내부 파라미터

| 항목 | 값 | 의미 |
|---|---:|---|
| `fx` | 2025.17 px | 가로 방향 초점거리 |
| `fy` | 2039.07 px | 세로 방향 초점거리 |
| `cx` | 969.79 px | 광학 중심의 가로 좌표 |
| `cy` | 459.43 px | 광학 중심의 세로 좌표 |

적재 높이 계산에는 세로 방향 초점거리 `fy = 2039.07 px`를 사용한다.

## 검증 결과

60 cm 거리에서 실제 크기가 22 × 17.5 cm인 마우스패드를 측정한 결과,
높이 방향 기준 약 98.24%의 정확도를 확인했다.

위 결과는 해당 거리와 촬영 조건에서 수행한 단일 기준물 검증 결과이다.
카메라 해상도, 화각 또는 디지털 줌 설정이 변경되면 다시 캘리브레이션해야 한다.

# 2. 온보드 (Jetson USB 카메라) — 2026-07-31

포크 정렬(S15P11A304-152)의 요각·거리를 **절대 단위**로 내기 위한 값. 이것이 없으면
`AlignError.yaw_deg`·`distance_mm`이 `None`이고 DoD의 "요각 ±5°"를 판정할 수 없다.

## 사용 장비

- 카메라: USB(UVC) 모듈, Jetson `/dev/video0`, **1280 × 720**
- 체커보드: **스테이션과 동일** — 9 × 6 내부 코너, 한 칸 24 mm
- 도구: `ai/scripts/calibrate_camera.py` (촬영 `shoot` / 풀이 `solve`)
- 촬영 시 `--rotate180` (카메라를 뒤집어 장착)

## 카메라 내부 파라미터

| 항목 | 값 | 비고 |
|---|---:|---|
| **`fx`** | **1277.65 px** | ← **포크 정렬에 쓰는 값** |
| `fy` | 1284.13 px | fx와 0.5% 차 (정사각 픽셀, 정상) |
| `cx` | 630.65 px | 화면 중앙 640에서 9px |
| `cy` | 306.82 px | |
| 재투영 RMS | **0.312 px** | 합격선 0.5 통과 |
| 사용 장수 | 18 / 20 | 흔들린 2장 자동 제외 |

왜곡: `[-0.237665, 1.114489, -0.000914, -0.003143, -1.492558]`

원본 `calibration.json`은 젯슨 `~/calib/shots/`.

## 신뢰 근거 (독립적인 셋)

1. **RMS 0.312 px** — 첫 시도 3.649에서 열 배 개선
2. **`cx`가 화면 중앙에 근접**(630.7 vs 640). 해가 발산하면 여기가 먼저 튄다 — 실패한
   시도에서는 92.98(왼쪽 끝)이 나왔다
3. **모델을 5가지로 바꿔도 `fx` 변동 0.1%**(1304.0~1305.3). 실패한 시도에서는
   1442~1612로 흔들렸다
4. 화각 환산 대각 **59.9°** — USB 카메라 모듈의 전형값

## ⚠️ 실패에서 배운 것 — 블러가 자세 다양성보다 먼저다

첫 두 번의 촬영이 실패했고 **원인은 자세가 아니라 모션 블러**였다.

움직이는 중에 저장된 장이 20장 중 14장이었고, 선명도와 재투영 오차가 정확히 반대로
갔다 — 선명도 70~208인 장이 5~6.5px, 455~557인 장이 0.44~0.86px. 전체 RMS 3.65px.

**자유 파라미터를 줄여도(광학중심 고정 등) RMS가 안 내려갔다.** 그것이 "모델 문제가
아니라 데이터 문제"라는 신호였다. 코너는 서브픽셀로 잡히므로 몇 px만 흘러도 그대로
오차가 된다.

→ `calibrate_camera.py`는 이제 **직전 프레임 대비 코너 이동이 1px 미만일 때만 저장**한다.
촬영 안내도 "자세를 바꾸세요"에서 **"자세 잡고 멈추세요"** 로 바꿨다.

## ⚠️ 카메라를 옮기면 무엇이 바뀌나

| | 카메라 재장착 시 |
|---|---|
| `fx`·`fy`·`cx`·`cy`·왜곡 | **그대로** — 렌즈·센서의 성질이다 |
| `fork_center_x` | **다시 재야 한다** — 포크 중심선의 화면 x |
| `ALIGN_ENTER_MM`·`INSERT_ENTER_MM` | **다시 재야 한다** |

거리 임계가 장착에 종속되는 이유: "구멍이 화면에서 사라지는 거리"는 카메라의 **높이와
내려다보는 각**에 달렸다. 각 θ가 커지면 개구가 `9.5 × cosθ`로 납작해져(라벨 가이드 §5)
더 먼 거리에서 이미 안 보인다.

**해상도를 바꿔도 다시 해야 한다** — 초점거리는 픽셀 단위다. 다만 가로 해상도가 같으면
(1280×720 → 1280×800 등) `fx`는 유지된다.

## 미완 — 거리 임계 실측 (파츠 대기 중)

`fork_servo`의 `ALIGN_ENTER_MM`(**650**) · `INSERT_ENTER_MM`(180)은 **아직 추정값**이다.
카메라 고정 파츠를 3D 프린트한 뒤 실측해야 한다.

> 2026-08-03 예정이었으나 **출력이 안 나와 밀렸다.** 파츠 없이 손으로 각도를 잡으면
> 매번 달라져 조정해봐야 파츠 붙이면 다시 해야 한다.

⚠️ **`ALIGN_ENTER_MM` 은 임의로 고치면 안 된다 — 만족해야 할 산수가 있다.** 최소
회전반경 53.7cm 기준 좌우 오프셋 10cm 를 지우는 데 전진 45cm 가 필요하고, 그 거리는
ALIGN 구간에서만 벌 수 있으므로:

    ALIGN_ENTER_MM ≥ INSERT_ENTER_MM + 450

종전 값 350 은 이 조건을 깨고 있었다(ALIGN 구간이 170mm 뿐) — **10cm 틀어져 있으면
기하학적으로 못 고치고 반드시 ABORT** 한다. 2026-08-03 에 650 으로 고쳤다(S15P11A304-191).
실측값을 넣을 때도 이 부등식을 확인할 것.

⚠️ **px 임계는 손으로 고르지 않는다.** `ALIGN_ENTER_PX`·`INSERT_ENTER_PX` 는 위 mm
값에서 유도된다(`span_px = fx × 48.5 / distance_mm`). 따로 고르면 **같은 이름인데 다른
거리**가 되어, `--focal-px` 를 주느냐 마느냐로 동작이 갈린다(실제로 그랬다).

측정 도구는 준비돼 있다 — `ai/scripts/pallet_ruler.py`:

```
PYTHONPATH=src python3 scripts/pallet_ruler.py \
    --engine ~/trt_test/onboard_s640_ep116_fp16.engine \
    --plugin ~/mmdeploy/build_trt/lib/libmmdeploy_tensorrt_ops.so \
    --camera 0 --rotate180 --focal-px 1277.7
```

Ctrl-C 시 요약이 나온다:
- **구멍이 보인 가장 가까운 거리** → `INSERT_ENTER_MM`의 상한
- **파렛트가 잡힌 가장 먼 거리** → `ALIGN_ENTER_MM`의 상한

같은 자리에서 `fork_center_x`(포크 중심선의 화면 x)도 같이 잰다.

⚠️ **반드시 차에 장착한 상태로** 재야 한다. 손으로 들면 높이·각도가 제멋대로라 그 값을
차에 쓸 수 없다. 다만 **주행은 필요 없다** — 세워두고 파렛트만 밀었다 당기면 된다.
