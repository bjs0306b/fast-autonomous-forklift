# FR-201 적재 공간 인식

## 1. 목적

통제된 Isaac Sim 환경에서 랙 배치가 확정된 이후, 랙과 적재 위치 정보를 관제 시스템에 등록하고
가용 적재 공간을 관리하기 위해 필요한 정보와 담당 기능 사이의 연동 절차를 정의한다.

FR-201의 현재 목표는 랙 관련 값을 미리 확정하거나 기능을 직접 구현하는 것이 아니다. Isaac Sim MVP
환경이 완성된 뒤 각 담당자가 동일한 정보를 사용할 수 있도록 작업 순서와 필요한 정보의 종류를
정리하는 데 목적이 있다.

## 2. 현재 상태

현재 Isaac Sim 창고 환경이 완성되지 않았으므로 랙의 형태나 위치는 미정이다.
실제 값은 Isaac Sim MVP 환경이 확정된 이후 협의하여 결정한다.

## 3. MVP 우선 구현 방향

첫 번째 목표는 동적으로 랙을 탐색하거나 창고 구성을 변경하는 시스템이 아니라, 사전에 구성된
통제 환경에서 적재 공간 정보를 관리하는 MVP를 구현하는 것이다.

MVP에서는 다음 조건을 전제로 한다.(대충 통제된 환경에서 실행한다는 뜻)

- Isaac Sim에 배치한 랙의 위치와 구조는 실행 중 변경되지 않는다.
- 확정된 랙과 적재 위치 정보는 관제 DB에 초기 데이터로 등록한다.
- 관제 시스템이 랙과 적재 위치의 현재 상태를 관리한다.
- 시스템을 통하지 않고 랙 배치나 화물 위치를 임의로 변경하지 않는다.
- 적재·하역 작업 결과를 기준으로 관제의 적재 위치 상태를 갱신한다.
- 환경 자동 탐색과 동적 랙 추가는 MVP 이후 확장 기능으로 남긴다.

## 4. 진행 순서

### 4.1 Isaac Sim 환경 구성

Isaac Sim 담당자가 MVP에서 사용할 창고와 랙을 배치한다.

이 단계에서 다음 내용이 결정된다.

- 사용할 랙 모델
- 랙 개수
- 랙별 위치와 방향
- 랙의 층·열 구조
- 초기 화물 배치

### 4.2 랙·적재 위치 정보 확정

Isaac Sim 환경이 완성되면 Isaac Sim 담당자와 협의한다.

- 랙과 적재 위치의 식별 방법
- 관제 화면에 표시할 이름
- 관제 DB에 등록할 필드
- 초기 점유 상태
- 적재·하역 결과에 따른 상태 변경 방법

### 4.3 관제 DB 초기 데이터 등록

확정된 랙과 적재 위치 정보를 관제 DB에 초기 데이터로 등록한다.

등록 대상에는 다음 정보가 포함될 수 있다.

- 랙 식별 정보
- 랙의 층·열 구조
- 적재 위치 식별 정보(랙 ID·층·열)
- 적재 위치 초기 상태
- 랙과 적재 위치의 사용 가능 여부

구체적인 테이블 구조와 등록 방식은 백엔드 담당자와 협의한다.

### 4.4 시스템 연동

관제가 선택한 랙 접근 위치를 ROS2/Nav2에 전달하고, 작업 실행 결과를 받아 적재 위치 상태를 갱신한다.

```text
Isaac Sim MVP 환경 확정
        ↓
랙·적재 위치 정보 합의
        ↓
관제 DB 초기 데이터 등록
        ↓
SLAM 지도 생성 및 좌표계 정렬
        ↓
랙 접근 좌표 등록
        ↓
FR-202가 가용 적재 위치 선택
        ↓
AMCL 위치 추정 + Nav2 이동
        ↓
적재·하역 작업 결과 반영
```


## 5. 담당자 간 확정이 필요한 항목

### Isaac Sim 담당자와 확인

- MVP 랙 개수와 모델
- 랙 위치와 방향
- 랙의 층·열 구조

### 관제 or 백엔드 담당자와 확인

- 랙·적재 위치 정보를 저장할 데이터 구조
- 가용 적재 위치를 조회하는 방식

## 6. 후속 구현 참고사항

아래의 JSON 구조는 확정이 아니며 검토할 수 있는 참고사항이다.

### 6.1 식별자 참고

적재 위치는 다음 값의 조합으로 구분할 수 있다.

```text
rackId
level
column
```

### 6.2 랙 정보 참고

관제에서 랙을 관리할 때 다음 필드가 필요할 수 있다.

```json
{
  "rackId": "TBD",
  "name": "TBD",
  "levels": null,
  "columns": null,
  "active": true,
  "approachPose": null
}
```

- `rackId`: 랙 식별자
- `name`: 관제 표시 이름
- `levels`, `columns`: 랙의 층, 열
- `active`: 랙 사용 가능 여부
- `approachPose`: 맵 생성 이후 확정할 랙 접근 위치

### 6.3 적재 위치 정보 참고

관제에서 적재 위치를 구분할 때 다음 필드를 사용할 수 있다.

```json
{
  "rackId": "TBD",
  "level": null,
  "column": null
}
```

- `rackId`: 랙 ID
- `level`: 층 번호
- `column`: 열 번호
- `TBD`, `null`: 미확정 값

### 6.4 적재 위치 상태 참고

MVP에서는 적재 위치 상태를 하나의 속성으로 관리한다.

```text
EMPTY
RESERVED
OCCUPIED
UNKNOWN
```

- `EMPTY`: 적재 가능
- `RESERVED`: 작업 예약됨
- `OCCUPIED`: 화물 적재됨
- `UNKNOWN`: 상태 확인 불가

### 6.5 랙 접근 위치 참고

SLAM 지도와 좌표계가 확정된 이후 랙 접근 위치에 다음 값이 필요할 수 있다.

```json
{
  "x": null,
  "y": null,
  "heading": null,
  "frameId": "map"
}
```

- `x`, `y`: 맵 기준 위치
- `heading`: 랙을 바라보는 차량 방향
- `frameId`: 좌표 기준 프레임

정확한 필드명, 단위, 방향 범위는 ROS2/Nav2 담당자와 합의한다.

### 6.6 작업 결과 참고

적재·하역 작업 완료 후 관제가 적재 위치 상태를 갱신하려면 다음 정보가 필요할 수 있다.

```json
{
  "taskId": "TBD",
  "rackId": "TBD",
  "level": null,
  "column": null,
  "operation": "TBD",
  "result": "TBD",
  "completedAt": "TBD"
}
```

검토 가능한 값의 예:

- 작업 구분: 적재, 하역
- 작업 결과: 성공, 실패, 취소
- 작업 ID: 중복 결과를 구분할 수 있는 고유값
- 완료 시각: 프로젝트 공통 통신 시각 규격

실제 MQTT payload와 필드명은 통신·Isaac Sim·관제 담당자와 합의한다.
