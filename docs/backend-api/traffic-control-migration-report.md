## 0. 한 줄 요약

F팀이 파이썬(`demo_loop2.py`)으로 돌리던 관제를 백엔드로 옮겨 달라는 요청이다.
**아직 아무것도 구현하지 않았다.** 다만 문서를 읽는 과정에서 **이미 배포된 DB에 10배
오류**를 발견했고, **기존 교통 관제 코드가 F팀이 경고한 함정에 그대로 빠져 있음**을 확인했다.
이 두 건이 신규 구현보다 급하다.

## 1. 🔴 즉시 고쳐야 할 것 — `fork_height` 10배 오류

### 무엇이 틀렸나

| 출처 | 선반 높이 |
|---|---|
| `rack_slots.csv` `place_z` | **1.325** |
| `backend-mqtt-guide.md` 높이 환산표 | **1.325** (실물 132.5 mm) |
| `backend-control-impl.md` `shelfHeight` | **1.325** |
| **DB `storage_slot.fork_height`** | **13.25** ← 🔴 10배 |

시드 파일 머리말이 인용한 8월 5일자 표에 `13.25`로 적혀 있었고 그대로 넣었다.
신규 문서 세 곳이 모두 `1.325`이므로 **DB 값이 틀렸다.**

### 영향

`fork_height`는 `task.dropoff.forkHeight`로 **변환 없이 그대로** 나간다
(`backend-mqtt-guide` §4.2). 즉 차량에 "포크를 13.25까지 올려라"가 전달된다.
문서상 **포크 최대치는 1.5**이므로 범위를 8배 넘는 값이다.

- 시뮬: 포크가 한계까지 올라가거나 명령이 거부된다
- 실물: 132.5 mm 올려야 할 것을 1325 mm로 해석한다

### 어디에 퍼져 있나

| 위치 | 상태 |
|---|---|
| `src/main/resources/db/seed-rack-slots.sql` | 🔴 24행 전부 `13.25` |
| 로컬 DB `storage_slot` | 🔴 적용됨 |
| **EC2 운영 DB `storage_slot`** | 🔴 **적용됨 (24칸 확인)** |
| `docs/backend-api/rack-slot-report.md` | 🔴 `13.25` 기준으로 서술 |

### 고치는 법

```sql
UPDATE storage_slot SET fork_height = 1.325
 WHERE slot_code REGEXP '^[AB][0-9]{3}$';
```

로컬·EC2 양쪽에 적용하고 시드 파일도 함께 고쳐야 한다.
**단, 아래 §2를 먼저 읽을 것** — 단위 가정이 함께 걸려 있다.

## 2. 🔴 "시뮬 좌표 = m" 가정이 F팀 문서와 어긋난다

2026-08-07 팀 결정으로 "시뮬 좌표를 그대로 미터로 본다"고 정하고 시드 주석에 반영했다.
그런데 신규 문서는 명시적으로 **시뮬 = 실물 × 10**이라고 못박는다.

> 실물 세트장은 그 1/10 인 2 × 3 m 이고, 변환은 실물 차량(오린카)이 자기 쪽에서 합니다
> (보낼 때 ×10, 받을 때 ÷10).
> — `backend-mqtt-guide` §2

`rack_slots.csv`에도 두 계열이 나란히 있다.

```
A1  approach_x 5.0   →  real_approach_x 0.5     (÷10)
    place_z    1.325 →  real_place_z    0.1325
```

### 백엔드가 실제로 해야 하는 일은 바뀌지 않는다

> **백엔드는 아무 변환도 하지 않습니다.** 받은 좌표를 그대로 쓰고, 목표도 시뮬 좌표로 보내면 됩니다.

즉 **DB에는 시뮬 값을 넣는 게 맞다.** 다만 그 값이 `13.25`가 아니라 `1.325`다.
"시뮬 = m" 표현은 잘못된 정리이므로 시드 주석과 보고서를 정정해야 한다.

### 🔴 파생 문제 — `usable_height` 2.00 이 무의미하다

높이 판정만 단위가 다르다.

> `height` 만 실물 미터입니다 (카메라 측정값을 그대로 전달하기 때문).

`PlacementService`는 `usable_height`를 카메라가 잰 `cargoHeight`(실물 m)와 비교한다.
그런데 문서상 **화물 전체 최대 높이가 시뮬 1.11 = 실물 111 mm = 0.111 m**다.

```
requiredHeight = 0.111 + 팔레트 0.12 + 여유 0.25 ≈ 0.48 m
usable_height  = 2.00 m
```

**모든 화물이 무조건 통과한다 — 높이 검사가 사실상 꺼져 있다.**
직전 값 1.00으로도 이미 전부 통과했으므로, 8월 7일의 `1.00 → 2.00` 변경은
**해결한 문제가 없었다.** (당시 "0.63 m 초과 거부"라고 보고했으나, 실제 화물이 0.111 m라
애초에 걸릴 일이 없었다.)

실제 제약은 **선반 간격**이고, 그 값은 아직 어느 문서에도 없다.

## 3. 🔴 기존 교통 관제가 F팀이 경고한 함정에 빠져 있다

FR-502-1a로 구현한 `traffic` 패키지는 **유클리드 거리**로 차간을 판정한다
(`CollisionPredictor.distance` / `currentGap` / `predictedGap`).

F팀 문서 §10 "흔한 함정" 첫 줄이 정확히 이것이다.

> | 유클리드 거리로 차간 판정 | 반대편 통로 차를 앞차로 착각해 엉뚱하게 멈춤 |

그리고 §2에서 이유를 든다.

> 왼쪽 통로(x=5)와 오른쪽 통로(x=15.5)는 직선으로 **10.5**지만 경로상으로는
> **반 바퀴(약 33)** 떨어져 있다.

`HOLD_DIST`가 9.0이므로 **두 통로의 차량이 10.5 떨어져 있어도 아슬아슬하게 안 걸리지만**,
모서리 근처에서는 충분히 오판이 난다.

### 필요한 것 — 호장(arc-length) 투영

순환로 폴리라인 위로 투영해 시작점부터의 거리 `s`로 바꾸고, `gap = (s_other − s_me) mod 67.0`
으로 앞뒤를 가린다. 참조 구현이 `nav2/scripts/track.py`(60줄)이고, 문서에 Java 번역본이
그대로 실려 있어 **이식 자체는 크지 않다.**

기존 `CollisionPredictor`의 예측 로직(`predictPosition`, `isClosing`)은 유지할 수 있고,
**거리 계산부만 교체**하면 된다.

## 4. 차량 ID — 이미 맞춰져 있다 ✅

F팀이 `sim01, sim02` → `sim02, sim03`으로 바꿨다고 "깨짐"으로 표시했으나,
백엔드는 이미 대응돼 있다 (`application-local.yml:71-74`).

```
sim01 → SIM-F01     sim02 → SIM-F02
sim03 → SIM-F03     fk01  → REAL-F01
```

별칭표에 네 개가 다 있어 **조치 불필요**하다.

## 5. 신규 구현 범위 — 아직 하나도 안 됨

### 5.1 있는 것 / 없는 것

| 요구 | 현재 | 비고 |
|---|---|---|
| telemetry 수신 | ✅ | 동작 확인됨 |
| 정지/재개 발행 | ✅ | `control` HOLD/RESUME/ESTOP |
| 목적지 발행 | ✅ | `task` |
| 랙 적재 지시 | ⚠️ | `cargo` 발행은 있으나 `place_rack` 액션 미확인 |
| 차간 판정 | ⚠️ | 있으나 유클리드 (§3) |
| **호장 투영** | 🔴 | 없음 |
| **순환로 모델** | 🔴 | 없음 (모서리 4개, 둘레 67.0) |
| **합류 순서 제어** | 🔴 | 없음 (규칙 0) |
| **바이 예약** | 🔴 | 없음 (규칙 3) |
| **정체 감시** | 🔴 | 없음 (규칙 4) |
| **주기 상태기계** | 🔴 | 없음 (6단계) |
| **랙 배정표** | 🔴 | 없음 |
| **운행 상태(OperationState)** | 🔴 | 없음 |
| **`/api/operation/*`** | 🔴 | 없음 |
| 연결 판정(3초 LOST) | 🔴 | 없음 |

`/api/vehicles`는 세 컨트롤러에 이미 있으나, F팀이 요구하는 응답 모양
(`phase`, `joined`, `held`, `cycles`)과 다르다.

### 5.2 규모 감각

문서가 요구하는 것은 **관제 엔진 하나를 새로 쓰는 일**이다.

- 순환로 모델 + 호장 투영 (`Track`) — 문서에 Java 코드가 그대로 있음, 작음
- 규칙 0~5 여섯 개 — 각각 의사코드 제공됨, 중간
- 주기 상태기계 6단계 — 전이 조건표 제공됨, 중간
- 0.5초 tick 스케줄러 — 작음
- REST 8개 + WebSocket 브로드캐스트 — 중간
- 운행 상태 관리 — 작음

의사코드가 상세해서 설계 부담은 낮지만, **양이 많고 통합 테스트가 어렵다**
(F팀 데모를 꺼야 3단계 이상 검증 가능).

## 6. F팀 문서 안에서 아직 안 정해진 것

| 항목 | 내용 |
|---|---|
| `arrived` 토픽 접두사 | 혼자 `forklift/`를 씀. 통일 여부 미정 |
| AI 연동 주체 | `arrived` 받아 `cargo` 발행하는 게 AI인지 백엔드인지 |
| 실물 `arrived` | C팀 미구현 |
| 주기 종료 조건 | 지금은 무한 반복 |
| 인증서 SAN | CN이 IP라 hostname 검증을 꺼야 함 (재발급 가능한지) |

**`arrived` 주체가 안 정해진 것이 구현에 직접 걸린다** — 주기 상태기계의 `LOAD` 단계
진입 트리거이기 때문이다.

## 7. 권고 — 순서

### 지금 (발표 전)

| # | 할 일 | 이유 |
|---|---|---|
| 1 | `fork_height` 13.25 → 1.325 (로컬·EC2·시드) | 🔴 **잘못된 값이 이미 운영 DB에 있다** |
| 2 | 시드 주석·보고서의 "시뮬 = m" 정정 | 후속 작업자가 같은 오해를 한다 |
| 3 | `usable_height` 근거 확보 또는 "검사 미동작" 명시 | 지금 값은 아무것도 거르지 않는다 |

**1번만 SQL 한 줄이고 나머지는 문서다.** 시연 전에 끝낼 수 있다.

### 발표 후

F팀이 권하는 순서를 그대로 따르는 것이 맞다.

```
① telemetry 수신 → 화면 표시          ✅ 이미 됨
② 정지/재개                            ✅ 이미 됨
③ 목적지 지시                          ✅ 이미 됨  (F팀 데모 꺼야 검증 가능)
④ 교통 규칙 전체 이식                  🔴 여기부터
```

④를 다시 쪼개면:

1. `Track` (호장 투영) — 문서 코드 이식, 단위 테스트로 검증 가능
2. 기존 `CollisionPredictor`의 거리 계산부를 `Track.gap`으로 교체 (§3)
3. 순환로 주행 + 규칙 1·2
4. 주기 상태기계 + 랙 배정
5. 규칙 0·3·4 (합류·바이 예약·정체)
6. `OperationState` + REST + WebSocket

**1·2번은 기존 코드를 고치는 일이라 먼저 해도 손해가 없다.** 지금 유클리드로
잘못 판정하는 것을 바로잡는 것이므로, 나머지를 못 하더라도 가치가 있다.

- **선반 간격(`usable_height`)의 실제 값** — 어느 문서에도 없다
